# uPil 答辩与面试问答

## Q1：为什么项目要采用多智能体，而不是一个大模型直接回答？

**答：** 素质教育客服同时包含公开知识问答和个人学情查询，两类请求的数据来源、权限要求和错误代价不同。Supervisor 负责识别意图和分流，FAQ 智能体只检索已审核知识，学情分析智能体只访问授权的结构化数据。这样可以把权限、工具和提示词约束放在明确边界内，降低模型越权和编造数据的风险，也便于分别测试和替换智能体。

## Q2：为什么第二个核心智能体选择学情分析，而不是报表智能体？

**答：** MVP 首先解决家长高频且有明确价值的问题：剩余课时、消课、出勤和阶段学习摘要。学情分析智能体直接服务家长和教师，能形成“查询事实 + 给出解释 + 必要时转人工”的闭环。报表生成可以作为后续能力，复用同一套结构化查询、确定性统计和任务产物模型，不在首期扩大范围。

## Q3：为什么项目最终移除了 A2A？

**答：** 当前个人学情、家长报告和教师班级报告都在同一代码库、同一权限域和同一部署单元内，统计由数据库确定性计算，正文由本地固定模板生成。A2A 在这里没有获得独立团队、独立扩缩容、异构运行时或高资源任务隔离收益，却增加了子服务、端口、令牌、状态映射、健康检查、重试和协议测试成本。因此项目最终删除 A2A/DSH，统一为同进程 `learning_analysis_agent`。这不是否定协议；未来出现明确的跨团队或独立部署边界时再重新评估。

## Q4：为什么采用 MinIO，不把报告 PDF 存 PostgreSQL 或 MongoDB GridFS？

**答：** 家长和教师学情报告 PDF 是非结构化产物，MinIO 更适合对象键、私有桶、生命周期和备份；PostgreSQL 只保存报告任务、对象键、SHA-256、大小和页数，便于业务查询、鉴权和审计。浏览器不直接访问 MinIO，下载必须经过后端重新校验家长绑定关系或教师授课关系，并复核文件完整性。教师媒体工作台已经下线，当前 uPil 的 MinIO 适配器不再保存图片，也不提供图片预签名 URL。MongoDB GridFS 虽然可行，但会增加数据库类型和运维复杂度，对当前报告闭环没有额外收益。

## Q5：RAGFlow 和向量数据库分别负责什么？

**答：** RAGFlow 是知识库处理与检索层，负责文档解析、分块、表格、OCR、图片说明、召回和来源引用。当前优先使用 RAGFlow 默认的向量/混合检索能力，不额外引入 Qdrant 或 Milvus。这样可以先验证业务问答质量；当规模和性能指标证明需要独立向量服务时，再拆分后端。

## Q6：图片放进知识库后，模型真的能理解图片吗？

**答：** 不能把“保存图片”和“理解图片”等同。知识原件由 RAGFlow 自身的知识库基础设施管理，RAGFlow 负责 OCR、图片说明或多模态解析，再把可检索文本和来源引用返回 uPil。uPil 只消费经过治理的检索结果，不管理原图、不生成图片下载地址。对教师照片、环境图等内容，回答只能依据审核后的标题、替代文本和说明，不能仅凭图片外观推断教师资质或学员信息。

## Q7：为什么接口采用 SSE？

**答：** 客服回答可能需要路由、检索、模型生成等多个步骤。SSE 适合服务端持续向浏览器推送单向事件，接入简单、浏览器支持好，用户能更早看到状态和文本。项目中需要区分 status、token、complete 和 error 事件，并保证完成事件包含路由、提供方和来源摘要。若未来需要双向控制、音视频或大量并发连接，再评估 WebSocket。

## Q8：如何避免模型编造课时和出勤数据？

**答：** 课时和出勤属于结构化业务事实，由 SQL 查询和确定性统计得到。个人摘要由受控处理器组织，家长和教师 PDF 正文使用本地固定模板，不让模型生成或改写数字。查询前先做用户、角色和学员绑定校验；没有权限就拒绝或转人工。回答中带统计对象和时间范围，不把模型自由生成的数字当作事实。

## Q9：RAG 检索错了怎么办？

**答：** 使用固定评测集检查召回、事实准确率、来源可追溯性和转人工率。课程、收费、退费和校区规则带版本与有效期；发生冲突或低置信度时不强行回答，转人工。失败案例加入评测集，文档修订后重新索引并回归。

## Q10：当前项目哪些内容还不能宣称完成？

**答：** 当前完成的是多 Agent 对话编排、结构化学情工具、家长/教师单 PDF 报告链路、报告 MinIO 适配器、RAGFlow 接口边界、招生意向旁路和离线自动化测试。教师媒体工作台和 A2A/DSH 已主动退出当前产品与运行边界，不能再表述为现行能力。项目尚未完成真实 MinIO、RAGFlow、OIDC、PostgreSQL、机构数据和生产模型的整体验收，也没有完成生产容量、容灾和安全联调，因此只能说明本地可验证闭环已经完成，不能宣称大规模生产就绪。

## Q11：客户给的真实语料大概率是 PDF，你们为什么还要维护 Markdown？

**答：** 客户交付物确实多为 PDF，所以系统的语料入口必须支持 PDF，并且用 RAGFlow 的版面分析、OCR 和表格抽取完成解析。但 PDF 直接作为唯一知识源会有跨页表格、页眉页脚噪声和来源定位粗糙的问题。因此我们把 PDF 作为真实入口，解析后经过人工审核，再把高频规则固化为 Markdown 审核稿，用固定评测集验证。简单说：PDF 保证真实性，解析加审核后的结构化知识保证专业性和可维护性。

## Q12：PDF 直灌和清洗后 Markdown 的检索效果有什么区别？

**答：** 我们用同一批 P0 问题做过对比。清洗后的 Markdown 来源能精确到文档和小节，规则类问题命中稳定，页眉页脚噪声少；原始 PDF 能覆盖大部分信息，但来源多为页码，跨页表格可能被拆散，页眉页脚会混进片段。这正是我们坚持“PDF 入口 + 解析清洗 + 审核评测”的原因，也是项目可以量化的一个实验结论。

## Q13：直接使用 RAGFlow，会不会显得项目没有技术含量？

**答：** 关键不在于是否使用现成 RAG 平台，而在于是否解决了业务问题。RAGFlow 负责通用的文档解析、切片、向量化和检索基础设施；uPil 自己实现教育客服场景中的知识域路由、语料审核与版本管理、检索结果约束、结构化学情工具调用、敏感信息控制、来源返回、SSE 状态编排和离线评测。我们还会用同一批问题对比默认切块和优化切块的召回及回答质量。这样 RAGFlow 是可替换的基础组件，而不是项目的全部。

## Q14：为什么不自己实现向量库和切块算法？

**答：** 自己实现向量存储并不会自动带来业务价值，还会增加索引一致性、文档解析、表格处理、OCR、权限和运维成本。当前项目的难点是把非结构化机构资料转成可靠的客服知识，并和学员结构化数据、权限和人工兜底衔接起来。因此首期使用 RAGFlow 提高交付效率，同时通过 Adapter、语料治理、评测和路由设计保留替换空间。当数据规模、延迟或多租户隔离达到明确阈值时，再评估独立向量数据库。

## Q15：uPil 的 RAG 生产链路具体是怎样的？

**答：** 原始 PDF、图片和业务文档进入 RAGFlow 管理的知识库入口，并按组织流程完成授权、审核和版本治理；RAGFlow 根据资料类型完成解析、OCR、切片、BGE-M3 向量化、混合检索和来源引用；LangGraph Supervisor 根据意图选择 FAQ Dataset、结构化学情工具或人工协助；FAQ 只能根据有来源的片段回答，动态课时、出勤和班级统计必须查询受控业务工具；uPil 再做权限、敏感信息、规则冲突和低置信度检查，通过 SSE 返回状态、答案和脱敏来源。uPil 自身的 MinIO 只保存学情报告 PDF，不是 RAG 知识原件入口。

## Q16：如何证明 RAG 优化有效？

**答：** 建立包含课程咨询、课程价值、收费规则、边界案例、拒答和多轮问题的固定评测集，至少保留问题、标准答案要点、必须命中的来源和预期动作。使用同一模型、同一问题集比较默认配置与优化配置，记录 Recall@K、答案事实正确率、来源覆盖率、拒答准确率、工具调用准确率和端到端延迟。最终展示典型错误案例和修复前后的结果，而不是只展示控制台连接成功。
## Q17：为什么项目中要单独管理 pytest 临时目录？

**答：** 自动化测试会创建临时 SQLite 数据库、失败缓存和运行目录，这些不是源码，也不能与正式业务数据库混用。uPil 将它们统一放入 `.test-artifacts/pytest` 并加入 `.gitignore`，既能隔离测试数据，又能避免项目根目录被多轮回归产物污染。在 CI 中还可以按 Job 分配子目录，降低并发运行时的文件锁和互相覆盖风险。

## Q18：项目上传 GitHub 时如何防止 API Key 和业务数据泄露？

**答：** 首先在 `.gitignore` 中排除真实 `.env`、数据库、日志、测试产物、备份和外部嵌套仓库；其次在 `git add` 前对实际提交候选执行敏感信息模式扫描和大文件检查，再审查暂存区清单。仓库只提交 `.env.example` 配置模板，真实密钥由环境变量或 Secret Manager 注入。GitHub 登录通过本机 Credential Manager 或浏览器完成，不把 Token 写进命令、源码或聊天。已经暴露过的 Key 不能只删除文件，必须在对应平台撤销并轮换。

## Q19：为什么不把本地拉取的 RAGFlow 源码一起提交？

**答：** RAGFlow 是独立上游依赖，把完整源码和 `.git` 历史嵌入主仓库会引入大文件、许可证边界、历史噪声和克隆不完整等问题，也无法清晰表达 uPil 自己的贡献。uPil 只提交适配器、Compose 配置、版本说明和必要补丁，通过固定镜像或上游版本复现依赖。这样主仓库边界明确，也方便后续升级和安全扫描。

## Q20：报课意向 Agent 如何与主业务 Agent 并行？

**答：** 入口先本地提取并脱敏联系方式，再把脱敏消息同时交给主咨询链和报课意向旁路。主链照常完成 FAQ、服务规则或学情回答；旁路只输出有限证据码，不回答用户、不调用工具、不持有数据库会话。主回答结束时只等待旁路剩余的短超时预算，失败则走确定性规则，因此不会把招生识别变成咨询链路的硬依赖。

## Q21：如何保证高意向一定主动询问联系方式，又不滥收隐私？

**答：** 明确预约试听、明确报名或要求顾问联系由本地规则判为高意向。若没有已授权联系方式，后端状态机固定进入 `awaiting_contact_consent` 并通过 SSE 返回统一询问，模型不能遗漏或改写。联系方式虽然会在入口本地识别以便脱敏，但只有家长同一轮主动提供、同一轮明确授权，并且已有有效意向或当前轮同时表达明确动作时才加密保存。

## Q22：为什么不设置运营端和转化漏斗？

**答：** 项目要证明的是多 Agent 从正常咨询、意向识别到人工跟进的业务闭环，而不是建设完整 CRM。销售顾问老师仍使用 `teacher` 角色，只通过 `lead_followup` 最小权限访问线索；普通教师无权访问。运营账号、`lead_analytics` 和转化漏斗被取消，减少额外角色、聚合权限和隐私范围，也避免项目偏向通用后台管理系统。

## Q23：为什么不能只按 800 行拆文件？

**答：** 800 行只能作为维护门禁，不能代表单一职责。uPil 先按变化原因和依赖方向拆分：HTTP、Workflow、Service、Agent、Tool、Connector、Prompt 分层；再统计文件规模。当前最大生产文件为 485 行，超过 800 行为 0，但更重要的是 LangGraph State、路由、节点和 builder 已经拥有独立边界。

## Q24：为什么 LangGraph 要做到一个节点一个文件？

**答：** 每个节点的数据来源、权限和降级路径不同。将节点分开后，builder 只展示图拓扑，不夹带业务细节；单个节点可以独立测试和替换；复杂逻辑可以下沉到领域 Service，而不会让 `graph.py` 重新变成几百行的总控文件。

## Q25：为什么重构后仍保留旧模块？

**答：** 旧路径被测试、评估脚本、Uvicorn 和潜在外部调用方使用。项目采用兼容门面渐进迁移：旧文件只重导出新实现，不维护第二套逻辑；生产代码已直接导入新路径。这样既能重构目录，又能避免一次性破坏公开导入契约。

## Q26：FastAPI 路由拆出去后，怎样保证测试覆盖仍生效？

**答：** `Depends` 的 override 依赖函数对象身份，因此 `main.py` 和 Router 继续引用 `api/dependencies.py` 中同一个对象。对于历史 monkeypatch，`api.compat.main_symbol()` 在调用时读取 `backend.app.main` 的替换符号。这两个兼容点经过原有 API 全量回归验证。

## Q27：Tool、Connector、Workflow 和 Service 有什么区别？

**答：** Tool 执行一个确定性动作，不决定图路由；Connector 或 Integration 负责现行外部服务的协议、传输、超时和响应校验，不做业务授权；Workflow 决定调用顺序与分支；Service 维护领域规则、状态机和事务。Router 负责 HTTP 认证入口和响应映射。

## Q28：如何证明模块拆分没有改变业务？

**答：** 模块拆分没有修改 URL、Schema、鉴权规则、报告状态机和数据库迁移。后续架构收敛只删除了不再使用的远程 A2A 状态字段，业务接口仍以主系统 `report_task_id` 为准。报告专项、相关回归、全量测试、前端测试与构建、`compileall` 和 `git diff --check` 均作为最终验收门禁。

## Q29：为什么下线教师媒体工作台，却继续保留 MinIO 和 `media_asset_id`？

**答：** 教师素材上传、双人复核和图片访问的主要变化原因是内容管理与后台审核，继续扩展会让项目偏向通用管理系统，而不是多 Agent 咨询、学情分析、报告交付和招生线索闭环，因此当前版本删除了媒体页面、API、权限、业务表和图片存储方法。MinIO 仍然保留，因为家长和教师报告 PDF 的私有存储与鉴权下载是核心业务闭环的一部分；`SourceReference.media_asset_id` 也保留，但它只表示 RAGFlow 返回的外部来源标识，不对应 uPil 本地媒体对象。生产迁移 006 只清理旧权限和 `media_assets` 表，历史图片对象必须由运维盘点后按保留策略处理，不能在数据库事务中跨系统盲删。

当前退役专项为 `129 passed`，integrations 为 `24 passed`；报告专项为 `70 passed, 7 skipped, 3 warnings`，相关回归为 `100 passed, 3 warnings`，Windows 后端全量为 `393 passed, 8 skipped, 3 warnings`；前端 typecheck、`12 passed`、构建和后端静态资源同步均通过。

## Q30：为什么说向量数据库不等于 Agent 记忆系统？

**答：** 向量库只是某一种存储和召回组件，不能代替记忆准入、事实抽取、冲突处理、
版本治理、过期清理和隐私控制。uPil 把当前会话放入短期工作记忆，把少量稳定事实放入
结构化长期记忆，情景记忆保留可替换协议并默认关闭；不同数据按风险和查询方式选择不同
存储，而不是把全部聊天无差别向量化。

## Q31：uPil 的上下文压缩是如何做的？

**答：** 当前会话只保留最近若干轮原始消息，较早内容压缩为滚动摘要，并用近似 Token
预算裁剪摘要和历史。读取时先按租户、用户、角色、会话和学员作用域过滤，再由各 Agent
projector 生成最小上下文。压缩只服务当前会话连贯性，不会把敏感信息或动态业务事实
写入摘要；它也不会替代长期记忆的结构化治理。

## Q32：多个 Agent 为什么可以共享上下文，又不会互相污染？

**答：** 共享的是只读、不可变的 ContextEnvelope，包含当前请求允许的最小字段；每个
Agent 通过独立 projector 取自己的视图，只返回受约束的 AgentResult。Supervisor 的
路由、权限、身份和原始隐私字段不能由 Agent 结果覆盖，最终由 reducer 按白名单合并。
因此“共享”是受控事实和会话证据共享，不是让所有 Agent 读写一个可变全局字典。

## Q33：哪些信息允许写入长期记忆，哪些信息必须拒绝？

**答：** 当前只允许课程兴趣、上课时间偏好和孩子昵称。写入既可以来自显式“请记住”，
也可以来自确定性规则识别的高置信度、肯定且稳定的陈述，例如“孩子喜欢编程”。手机号、
邮箱、Token、密码、银行卡，以及动态课时、出勤、名额、报告状态和非白名单字段都会拒绝；
“可能喜欢”“暂时喜欢”“明天上午有空”等不确定或临时表达也不会固化。

## Q34：长期记忆写错或用户改口时怎么办？

**答：** 同值写入直接去重；自主判断发现不同值时安全跳过，只有用户显式要求修改才新增
版本并使旧版本失效。删除和恢复都要求完整的用户与学员作用域，避免一个孩子的记忆影响另一个孩子。数据库异常会回滚并让记忆能力
降级为空，不阻断主聊天。后续还可以在不改变聊天契约的前提下增加管理端审计或自动
衰减策略，但不会因此把动态业务数据放进长期记忆。

## Q35：为什么情景记忆没有强行接入嵌入模型？

**答：** 当前项目的主要价值是课程咨询、学情事实和招生线索，历史闲聊的语义召回并非
主链路刚需。没有稳定嵌入模型、评测集和隐私策略时，强行写入向量库可能召回噪声并增加
外部依赖。uPil 先保留 Episodic Memory 协议和 Noop 实现，未来有明确数据价值后再以
离线评测、准入阈值和删除能力为前提启用。

## Q36：记忆模块故障会不会导致客服不可用？

**答：** 不应导致。记忆读取、授权解析或写入失败都在边界内回滚、记录固定原因码并降级
为空；主聊天仍可依靠当前用户消息、受控会话窗口和业务工具继续处理。Redis 故障不会
伪造成功，读操作也不会偷偷刷新 TTL。这样既不隐藏基础设施故障，也不把可选增强能力
变成主业务硬依赖。

## Q37：为什么要限制生产 Python 文件不超过 800 行？

**答：** 800 行是维护门禁，不是架构本身。真正的拆分依据是变化原因和依赖方向：状态
Schema、图构建、节点、Prompt、Tool、Connector、Service 和 Router 分开。当前扫描中
超过 800 行的生产文件为 0；即使文件低于 800 行，只要同时承担授权、事务、外部通信
和路由，也仍需继续拆分。

## Q38：为什么短期会话使用独立 Redis？

**答：** 多实例 API 不能依靠各自进程内存，否则同一会话落到不同实例会产生状态分叉。
uPil 使用独立 Redis 共享已脱敏的最近轮次、滚动摘要和受控槽位，并通过 TTL 控制生命周期。
它不复用 RAGFlow Redis，因为知识库升级、缓存清理、版本和淘汰策略不应影响客服会话。
Redis 模式启动时先 Ping，故障显式失败而不静默回退内存；本地 AOF 只证明重启恢复，
生产仍需要哨兵/集群、监控、容量告警和 Secret Manager。

## Q39：换一个 conversation_id 后为什么还能记得课程兴趣？

**答：** conversation_id 属于 Redis 短期会话键，只负责最近轮次、滚动摘要和当前槽位。
长期偏好存储在 PostgreSQL，按租户、认证用户、角色、学员和字段读取；来源会话编号只用于
最小审计，不作为查询过滤条件，因此新会话可以继承同一主体已经生效的稳定偏好。

## Q40：为什么长期记忆可以自主判断，却不直接交给大模型自由抽取？

**答：** 项目只需要三个低敏感字段，确定性规则更容易复现、解释和测试。自主判断要求
肯定、稳定表达和至少 0.85 的置信度，只能填补空白或同值去重，不能静默覆盖冲突；模型
自由抽取会扩大误写和隐私治理面。该取舍实现了必要的自主性，但没有为技术完整度过度设计。

## Q41：长期偏好如何避免污染 RAG 和动态业务回答？

**答：** Agent 只获得 key/value 安全投影。FAQ projector 仅在课程推荐或上课时间问题中
追加课程兴趣、时间偏好；昵称、内部主键、来源会话和作用域不进入检索。价格、名额、校区、
服务规则、课时和出勤仍查询权威知识或数据库工具，长期偏好不能覆盖动态事实。
