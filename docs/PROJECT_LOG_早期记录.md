## 关键技术原则

- LangChain 负责“调用能力”，LangGraph 负责“流程协作”。
- FastAPI 负责对外服务，业务服务层负责数据权限和安全。
- 对话接口采用 SSE，结构化查询和后台管理接口采用 JSON。
- 课时、消课、出勤、比例、阈值和名单由 SQL 或 Python 确定性计算。
- 大模型只负责意图理解、参数提取、结果组织和自然语言解释。
- 原始排课、考勤、消课和收费数据只读，智能体不能直接修改。
- 权限校验不能依赖 Prompt，必须在服务端执行。
- 模型、知识库和工具运行过程支持人工兜底、重试和审计。

## 新增技术评估：Deep Agents 与 RAGFlow

### 评估结论

1. **RAGFlow 可纳入正式架构**：作为独立的知识库解析、索引和检索服务，通过适配器与 LangChain/LangGraph 对接。
2. **Deep Agents 暂不作为一期默认架构**：其规划、文件系统、子智能体和长任务能力超出一期客服与基础学情查询的需要，可能增加行为不确定性、资源消耗和调试难度。
3. **一期推荐组合**：FastAPI + SSE + LangGraph 显式工作流 + LangChain 能力组件 + RAGFlow 知识库 + PostgreSQL 业务数据。
4. **后续可试用 Deep Agents**：优先用于复杂学情报告、运营分析或知识库维护等多步骤任务，并限制可调用工具和数据范围。

### 架构边界

- RAGFlow 负责文档解析、知识库管理、索引、检索和引用片段返回。
- LangChain 负责模型、Prompt、Retriever/HTTP 适配器、工具和结构化输出。
- LangGraph 负责 Supervisor、咨询智能体、学情分析智能体、状态、重试和人工兜底。
- PostgreSQL 负责用户、权限、课程、课时、出勤、会话和审计等结构化业务数据。
- 不同时运行 RAGFlow 与 pgvector 作为两套知识检索主链路；RAGFlow 接入后，pgvector 暂不作为一期知识库主存储。

### 主要风险

- RAGFlow 是独立服务，部署复杂度和内存占用高于 pgvector；
- RAGFlow 具体 API、版本和本地运行资源需要在后续阶段实测；
- Deep Agents 的自主规划不应直接拥有修改业务数据、访问未授权信息或执行营销动作的权限；
- 前端只接收经过过滤和脱敏的业务事件，不暴露内部工具参数、Prompt 或数据库字段。

## 解决的问题

原始需求功能范围过大，容易导致系统同时承担客服、教务、教学、运营和销售职责，增加开发、数据接入和验收难度。

## 处理方案

一期聚焦“智能客服 + 个人课时/出勤查询 + 教师班级基础统计 + 人工兜底”，先验证服务提效和课时/学情数据透明，再根据试点结果扩展试听、续班和运营能力。

### 遇到问题

1. Python 3.11 初始依赖安装受到 Windows 目录权限限制，补充 D:\\uPil\\.venv 和 site-packages 写权限后完成安装。
2. Python 3.11 TestClient 读取 SSE 流式响应的 response.text 时出现中文乱码，导致中文断言误报失败。
3. pytest 缓存目录和旧 __pycache__ 字节码存在权限警告。

### 解决方案

1. 通过 uv 将 Python 3.11.15 安装到 D:\\CodexData\\uv-python，再创建项目虚拟环境。
2. 测试改为使用 response.content.decode("utf-8") 解析 SSE，确认服务端 UTF-8 字节和中文内容正常。
3. 将 pytest 的可验证结果作为本轮测试依据；编译检查改用不落盘的 AST 语法检查，避免受到缓存目录权限影响。
