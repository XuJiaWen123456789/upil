# uPil 技术决策记录

## 1. 为什么采用 MinIO 保存学情报告 PDF

家长和教师学情报告 PDF 属于非结构化产物。将其放入对象存储，能够使用对象键、私有桶、版本和生命周期进行管理；业务数据库只保存对象键、摘要、大小和页数，避免大文件和业务事务混在一起。

MinIO 兼容 S3 API，适合私有部署，也便于未来迁移到兼容 S3 的云对象存储。uPil 通过报告存储适配器隔离 MinIO SDK，业务层不拼接内部地址、不签发图片 URL，也不向浏览器暴露访问密钥；报告下载必须经过后端重新鉴权和完整性复核。

## 2. 为什么不再使用 MongoDB GridFS

本项目当前核心业务事实是用户、学员、课程、课次、出勤、报告任务和招生线索，这些数据需要关系约束、权限查询和统计，优先放在 PostgreSQL。报告 PDF 则由 MinIO 负责。继续引入 MongoDB GridFS 会增加数据库类型、备份策略、运维连接和权限模型，无法直接提升当前核心业务价值，因此删除该依赖。

## 3. 向量数据库如何选择

当前不额外接入 Qdrant 或 Milvus，而是优先使用 RAGFlow 的默认向量/混合检索能力。项目需要的是“文档解析、表格、OCR、图片说明、切片、召回和来源引用”的完整知识库链路，RAGFlow 已经覆盖这些职责。单独引入向量数据库会增加部署、索引同步和排障成本。

当数据规模、跨知识库检索、独立检索服务或性能指标达到明确阈值时，再评估 Qdrant、Milvus 或其他后端；在没有压测数据之前，不提前堆叠基础设施。

## 4. RAGFlow 与 MinIO 的边界

RAGFlow 的职责是管理知识原件并把内容解析为可检索知识，包括正文、表格、OCR 文本、图片说明和来源信息。uPil 的 MinIO 适配器只负责报告 PDF，不负责知识素材。RAGFlow 返回给 uPil 的结果仍可包含文档/片段来源和 `media_asset_id` 等脱敏引用；该字段是外部来源协议标识，当前版本不据此读取本地对象或生成图片下载地址。

## 5. 生产安全约束

- 报告 MinIO 桶默认私有，应用使用只覆盖报告对象前缀的最小权限凭证。
- 前端不能直接提交角色和用户编号作为可信身份；正式环境应从 JWT、登录态或网关注入。
- 学员照片、身份证件和联系方式不得进入公开 FAQ 知识库。
- 报告对象必须复核 PDF 魔数、SHA-256、大小、页数和模板内容。
- SSE 只传递文本、来源摘要和外部来源 ID，不传二进制、访问密钥、对象键或内部存储地址。

## 6. RAGFlow 在 uPil 中的定位与技术边界

RAGFlow 适合作为 uPil 的 RAG 基础设施，但不把“上传文档并调用问答接口”作为项目的主要技术成果。RAGFlow 负责文档解析、版面识别、切片、Embedding、检索和来源信息；uPil 负责教育客服场景下的语料治理、知识库路由、权限控制、工具调用、回答约束、SSE 编排和质量评测。

采用这一边界的原因是：RAGFlow 已经解决了通用 RAG 中较重的文档处理问题，项目可以把工程重点放在真实业务中更关键的部分，即不同类型问题应该查什么知识、什么时候查询结构化系统、什么情况下必须拒答或转人工，以及如何证明回答有依据。

推荐的端到端链路如下：

1. 原始 PDF、图片和业务文档由 RAGFlow 的知识库基础设施接收，并按组织流程完成授权、审核和版本治理。
2. 语料导入流程按文档类型选择解析策略。课程手册使用 General 或 Manual，纯 FAQ 使用 Q&A，表格类资料单独验证，图片通过 OCR 或审核后的图片说明参与检索。
3. 解析结果进入 RAGFlow，使用 BGE-M3 进行向量化，并根据验证结果配置混合检索、关键词召回和重排能力。
4. 用户请求先经过 LangGraph Supervisor，识别为 FAQ、学情查询、业务办理或人工转接，再选择允许访问的 Dataset 和工具。
5. FAQ 智能体只使用检索片段生成答案，并返回来源摘要；课时、出勤、班级容量和退费核算等动态事实必须调用受控业务工具，不能从文档或模型记忆中编造。
6. uPil 对检索结果进行上下文拼接、敏感信息过滤、规则冲突检查和低置信度兜底，最后通过 SSE 返回状态、答案、来源和错误事件。
7. 使用固定评测集比较不同切块参数、检索配置和提示词版本，记录召回质量、回答正确率、来源覆盖率、拒答准确率和响应延迟。

因此，本项目的技术含量不在于重新实现一个向量数据库，而在于完成“文档入口到可审计客服回答”的业务化 RAG 工程闭环。

## 7. RAGFlow 使用方式的取舍

### 适合当前阶段的做法

- 采用 RAGFlow 作为独立检索服务，避免首期同时维护 Qdrant 或 Milvus。
- 保留 PDF 作为真实原始入口，先在 RAGFlow 解析，再由人工审核关键规则。
- 将课程、FAQ、收费与服务规则按知识域组织，避免所有内容混成一个无边界的大文档。
- 通过独立测试 Dataset 对比 256、384 和 512 等切块参数，再决定正式库配置。
- 在 uPil 代码中封装 RAGFlow Adapter，不让业务智能体直接依赖 RAGFlow 的页面或内部实现。

### 不足以支撑生产的做法

- 只使用默认 General 配置，不验证标题、表格和规则边界。
- 让大模型直接根据检索片段回答课时、余额、退费和班级名额。
- 没有知识版本、审核状态、来源引用和失败样本回流。
- 只展示一次“连接测试成功”，没有离线评测和回归结果。

结论：RAGFlow 不是低技术方案；把它当作黑盒问答插件才会显得技术含量不足。答辩中应展示至少一组基线与优化对比，以及一次从用户问题、Supervisor 路由、检索片段、工具调用到最终 SSE 回复的完整链路。

## 8. 报课意向采用旁路 Agent 与确定性状态机

报课意向识别不重构 FAQ 和服务规则主链，而是在 Supervisor 路由前对同一轮脱敏文本启动旁路 Agent。主 Agent 继续回答家长当前问题，旁路只输出严格证据码；短超时、模型异常或非法输出统一回退到确定性规则，不允许招生分析成为正常咨询的硬依赖。

模型只能补充低风险兴趣语义。明确试听、报名、顾问联系、联系方式授权和拒绝必须由本地规则命中；强度、队列、幂等、加密保存和状态迁移全部由代码控制。高意向缺少已授权联系方式时，由后端固定文案主动询问，不能交给模型自由生成。

## 9. 销售顾问是教师职责，不新增运营角色

项目继续保持 `parent` 和 `teacher` 两个业务角色。销售顾问老师使用 `teacher + lead_followup` 最小权限进入线索工作台；普通授课教师不会自动获得该能力。项目不提供运营账号、转化漏斗、`lead_analytics` 或 CRM 管理后台，避免把多 Agent 客服与学情助手扩张为通用后台系统。

联系方式在进入模型前本地脱敏，只有同一轮主动提供并明确授权、且存在有效意向时才使用 Fernet 加密保存。HMAC 指纹仅用于受控去重；明文只通过领取后的专用 no-store 接口短暂揭示，并记录最小审计。

## 10. pytest 运行产物为什么集中存放

Windows 环境下，pytest 默认临时目录可能受到文件锁和权限影响。早期为隔离不同轮次的 SQLite 测试数据库，使用了多个独立的 `--basetemp` 目录，但这会使项目根目录逐渐堆积临时文件。项目现统一使用 `.test-artifacts/pytest/cache` 保存可再生缓存，并使用 `.test-artifacts/pytest/runtime` 保存当前测试的临时数据库。

该目录不属于源码和业务数据，必须被版本控制忽略。固定目录减少根目录污染，也便于 CI 清理和磁盘监控；如果并行测试或多任务执行产生目录竞争，CI 应为每个 Job 在 `.test-artifacts/pytest/jobs/<job-id>` 下分配独立子目录，而不是重新把随机目录放回项目根目录。

## 11. Git 仓库边界与密钥治理

uPil 主仓库只维护本项目编写的业务代码、测试、部署模板、审核后的知识库语料和工程文档。为了本地联调而下载的 RAGFlow 上游源码及其他参考仓库属于外部依赖，不复制其 `.git` 历史，也不作为嵌套仓库提交；依赖版本应通过文档、镜像标签或锁定的版本号描述。

真实 `.env`、数据库、日志、测试产物、自动备份和本机 Docker 客户端状态一律排除。`.env.example` 可以提交，但只能包含空值、占位符或明确标注为开发示例的非敏感默认值；生产环境不得沿用示例密码。首次提交和后续 CI 均应执行敏感信息扫描与大文件检查。

GitHub 身份验证与应用运行密钥采用不同的安全边界：GitHub 凭据只交给本机 Credential Manager 或浏览器授权；RAGFlow、LLM、MinIO 和数据库密钥由环境变量或 Secret Manager 注入。任何曾经出现在聊天、截图或日志中的真实密钥都按已泄露处理并立即轮换，不能仅依赖从 Git 中删除。

## 12. 生产代码按能力边界拆分，800 行只作为门禁

项目收尾时不按固定行数机械切文件，而是按变更原因和依赖方向拆分：FastAPI
Router 负责 HTTP，Workflow 负责编排，Service 负责领域状态和事务，Agent 负责
模型识别，Tool 执行单一确定性动作，Connector 隔离仍存在的外部服务通信，Prompt 使用独立
文本资源。LangGraph 的 State、路由、builder 和节点分离，并保持一个节点一个文件。

生产 Python 建议控制在 500 行内，650 行触发职责复核，800 行禁止合入；测试文件
本轮按范围暂不拆分。行数不能替代架构评审：即使文件很短，只要同时处理授权、
事务、外部通信和图路由，仍然需要调整边界。

## 13. 渐进迁移优先于一次性删除旧导入路径

`main.py`、`graph.py`、`services/intent_recognition.py`、`services/report_tasks.py` 和
`tools/business_tools.py` 保留为兼容门面。它们只重导出新实现或
保留 ASGI/测试入口，不复制第二份业务逻辑。新生产代码必须直接导入新目录；测试、
评估脚本和外部调用方可以分阶段迁移，确认不再引用后再单独删除门面。

这样做是为了保留 `backend.app.main:app`、FastAPI dependency override 的函数对象
身份和既有 monkeypatch，而不是长期维护两套结构。`api.compat.main_symbol()` 只用于
旧测试替换点，不能演变为全局 Service Locator。

## 14. Prompt 资源化保留动态契约注入

稳定的角色说明、安全约束和输出格式要求存放在 `backend/app/prompts/*.txt`；Pydantic
JSON Schema、意图集合和课程白名单继续由 Python 在运行时注入。这样可以独立审阅
Prompt，又避免文本枚举与代码契约形成两套真相。Prompt loader 限定资源名并缓存
UTF-8 文本，节点和服务中不再嵌入大段提示词。

## 15. 下线教师媒体工作台，收缩到多 Agent 核心业务

教师素材上传、双人复核和图片预签名访问曾经作为阶段 14-E 的完整能力实现，但它的
主要变化原因是内容管理、素材授权和后台审核，不是咨询、学情分析、报告交付或招生
意向识别。继续保留会引入独立页面、权限点、业务表、文件校验和对象生命周期，使项目
逐渐偏向通用内容管理后台。

因此当前版本删除媒体 Router、Presenter、ORM 模型、权限函数、前端页面和图片 MinIO
方法；生产迁移 006 清理 `media_upload`、`media_review` 和 `media_assets`。历史阶段文档
保留用于说明取舍过程，不代表当前可用功能。报告 PDF 的私有桶和后端鉴权代理下载继续
保留，因为它们直接服务家长/教师报告闭环。`SourceReference.media_asset_id` 继续保留，
但只作为 RAGFlow 来源契约字段，避免为了产品范围收缩破坏外部协议兼容性。

## 16. 移除 A2A/DSH，统一为同进程学情分析 Agent

阶段 13 的 A2A/DSH 链路验证了跨进程任务契约、服务令牌、状态映射、超时重试和
故障隔离，但当前学情能力位于同一代码库、同一权限域，由同一团队维护，报告正文又
采用本地固定模板。此时独立协议和子服务没有获得独立部署、异构运行时或独立资源调度
收益，反而增加端口、令牌、健康检查、远程状态映射、重试和测试成本。

因此当前版本删除 A2A/DSH 运行代码、配置、容器和协议专项测试。Supervisor 将个人
摘要、家长报告和教师班级报告统一路由到一个 `learning_analysis_agent`；Agent 内部
根据意图分派给个人摘要、家长报告或班级统计处理器。统计值始终由数据库确定性计算，
报告正文由本地固定模板生成，Markdown 仅为当前请求内存中的 PDF 转换中间态。

多 Agent 表示职责、状态和工具边界，不要求每个 Agent 都是独立进程。报告任务幂等、
失败新尝试、MinIO 私有存储、补偿删除和动态下载鉴权继续由主系统负责，不依赖远程
协议。未来只有在分析能力由独立团队维护、需要独立扩缩容、采用异构运行时，或长耗时
任务确实需要跨服务调度时，才重新评估 A2A 或消息队列加内部 API 等方案。阶段 13
文档保留为历史实验记录，不代表当前运行架构。

## 17. 上下文与记忆采用受控分层治理

本轮不把“向量库”当作完整记忆系统，也不把所有历史对话永久拼入 Prompt。当前实现按
业务风险划分边界：ContextEnvelope 是单轮共享的不可变最小上下文；内存或 Redis
保存当前会话的工作记忆；PostgreSQL 只保存明确允许的少量结构化用户事实；情景记忆
保留可替换协议但默认使用 Noop 实现。未配置嵌入模型时不影响主聊天链路，情景记忆直接
关闭，避免为了“看起来完整”引入低质量召回。

上下文读取先做租户、用户、角色、会话和学员作用域隔离，再取最近轮次与滚动摘要，按
近似 Token 预算裁剪后交给各 Agent 的独立 projector。Agent 不能回写共享状态、覆盖
路由或权限；只有 reducer 按白名单合并结果。上下文压缩只针对当前会话的短期内容，
不把联系方式、Token、密码、银行卡、动态课时、出勤、名额和报告状态写入摘要或长期记忆。

长期记忆采用字段白名单和显式意图准入，目前只允许课程兴趣、上课时间偏好和孩子昵称。
同值去重，变化生成新版本并使旧版本失效；删除、恢复和冲突比较必须包含 learner_id
作用域，空值使用 SQL IS NULL，防止不同孩子之间互相操作。记忆功能是可选增强能力，
授权查询、读取和写入异常会回滚并降级为空记忆，不阻断主聊天 SSE。Redis 清理会避开
分布式锁键，读操作不刷新 TTL、不增加版本，故障则显式失败而不伪造成功。

本轮专项测试 26 passed，后端全量测试 419 passed、8 skipped、3 warnings。生产代码按
职责分层，800 行只是合入门禁而不是拆分唯一依据；当前扫描未发现超过 800 行的生产
Python 文件。具体目录、数据流、隐私边界和面试口径见
docs/技术方案/项目收尾_Agent上下文与记忆治理.md。

## 18. 短期会话默认切换为独立 Redis

当前本地运行、staging 和 production 配置模板均显式选择 Redis 作为短期会话后端；
`Settings` 的无环境默认值继续保留 memory，仅服务于单元测试和离线工具，防止导入配置
时隐式访问外部服务。uPil Redis 使用独立容器、数据卷、密码和端口，不复用 RAGFlow
内部 Redis/Valkey，避免知识库升级、缓存清理、淘汰策略或故障影响客服会话。

Redis 键按租户、用户、角色和会话形成主体隔离散列，值只包含已经脱敏的最近轮次、
滚动摘要、当前实体和受控槽位。每次原子更新使用短租约分布式锁，会话本身使用 TTL；
只读不续期、不增加版本。Redis 初始化失败显式阻止 Redis 模式启动，不静默降级到进程
内存，否则多实例会看到互相矛盾的上下文。健康检查只返回稳定状态，不回显连接地址或凭据。

当前本地实例使用 AOF everysec 提供开发重启恢复，但这不等同于生产高可用。生产仍需由
部署平台提供受监控的 Redis、Secret Manager、备份/故障转移和容量告警。结构化长期记忆
继续使用 PostgreSQL，情景记忆仍默认关闭，启用 Redis 不会改变两者的边界。

## 19. 结构化长期记忆采用“双准入、单字段、显式覆盖”

长期偏好只保存 `course_interest`、`class_time_preference` 和
`child_nickname` 三个低敏感字段，使用 PostgreSQL 精确查询，不引入新的向量数据库。
准入分为用户显式“请记住”和确定性规则识别的高置信度稳定陈述两类；后一类必须是肯定、
非临时表达，最低置信度为 0.85。每条消息只提取一个最明确候选，避免为了批量写入引入
复杂事务和难以解释的冲突顺序。
