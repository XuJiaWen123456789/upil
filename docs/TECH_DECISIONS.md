# uPil 技术决策记录

## 1. 为什么采用 MinIO 保存图片和文档原件

教育机构知识库中的教师展示图、校区环境图、课程表截图、PDF 和课件属于非结构化对象。将它们放入对象存储，能够使用对象键、桶策略、版本控制、生命周期和预签名 URL 进行管理；业务数据库只保存元数据，避免大文件和业务事务混在一起。

MinIO 兼容 S3 API，适合本地部署和答辩演示，也便于未来迁移到兼容 S3 的云对象存储。uPil 通过适配器隔离 MinIO SDK，业务层不直接拼接内部地址或暴露访问密钥。

## 2. 为什么不再使用 MongoDB GridFS

本项目当前核心业务事实是用户、学员、课程、课次、出勤和任务，这些数据需要关系约束、权限查询和统计，优先放在 PostgreSQL。媒体原件则由 MinIO 负责。继续引入 MongoDB GridFS 会增加数据库类型、备份策略、运维连接和权限模型，无法直接提升当前 MVP 的核心业务价值，因此删除该依赖，减少系统复杂度。

## 3. 向量数据库如何选择

当前不额外接入 Qdrant 或 Milvus，而是优先使用 RAGFlow 的默认向量/混合检索能力。项目需要的是“文档解析、表格、OCR、图片说明、切片、召回和来源引用”的完整知识库链路，RAGFlow 已经覆盖这些职责。单独引入向量数据库会增加部署、索引同步和排障成本。

当数据规模、跨知识库检索、独立检索服务或性能指标达到明确阈值时，再评估 Qdrant、Milvus 或其他后端；在没有压测数据之前，不提前堆叠基础设施。

## 4. RAGFlow 与 MinIO 的边界

RAGFlow 的职责是把可供问答的文档内容解析为可检索知识，包括正文、表格、OCR 文本、图片说明和来源信息。MinIO 的职责是保存原始文件。RAGFlow 返回给 uPil 的结果应包含文档/片段来源和 media_asset_id 等脱敏引用，原图下载由 uPil 校验权限后生成短时预签名 URL。

## 5. 生产安全约束

- MinIO 桶默认私有，应用使用最小权限凭证。
- 前端不能直接提交角色和用户编号作为可信身份；正式环境应从 JWT、登录态或网关注入。
- 学员照片、身份证件和联系方式不得进入公开 FAQ 知识库。
- SVG 上传需要消毒或转换为安全的 PNG/WebP。
- 所有媒体资产记录 SHA-256、大小、审核状态、来源文档和可见范围。
- SSE 只传递文本、来源摘要和媒体资产 ID，不传二进制、访问密钥或内部存储地址。

## 6. RAGFlow 在 uPil 中的定位与技术边界

RAGFlow 适合作为 uPil 的 RAG 基础设施，但不把“上传文档并调用问答接口”作为项目的主要技术成果。RAGFlow 负责文档解析、版面识别、切片、Embedding、检索和来源信息；uPil 负责教育客服场景下的语料治理、知识库路由、权限控制、工具调用、回答约束、SSE 编排和质量评测。

采用这一边界的原因是：RAGFlow 已经解决了通用 RAG 中较重的文档处理问题，项目可以把工程重点放在真实业务中更关键的部分，即不同类型问题应该查什么知识、什么时候查询结构化系统、什么情况下必须拒答或转人工，以及如何证明回答有依据。

推荐的端到端链路如下：

1. 原始 PDF、图片和业务文档进入 MinIO，记录文件哈希、版本、来源、可见范围和审核状态。
2. 由 uPil 的语料导入流程按文档类型选择解析策略。课程手册使用 General 或 Manual，纯 FAQ 使用 Q&A，表格类资料单独验证，图片通过 OCR 或审核后的图片说明参与检索。
3. 解析结果进入 RAGFlow，使用 BGE-M3 进行向量化，并根据验证结果配置混合检索、关键词召回和重排能力。
4. 用户请求先经过 LangGraph Supervisor，识别为 FAQ、学情查询、业务办理或人工转接，再选择允许访问的 Dataset 和工具。
5. FAQ 智能体只使用检索片段生成答案，并返回来源摘要；课时、出勤、班级容量和退费核算等动态事实必须调用受控业务工具，不能从文档或模型记忆中编造。
6. uPil 对检索结果进行上下文拼接、敏感信息过滤、规则冲突检查和低置信度兜底，最后通过 SSE 返回状态、答案、来源和错误事件。
7. 使用固定评测集比较不同切块参数、检索配置和提示词版本，记录召回质量、回答正确率、来源覆盖率、拒答准确率和响应延迟。

因此，本项目的技术含量不在于重新实现一个向量数据库，而在于完成“文档入口到可审计客服回答”的业务化 RAG 工程闭环。

## 7. RAGFlow 使用方式的取舍

### 适合当前阶段的做法

- 采用 RAGFlow 作为独立检索服务，避免首期同时维护 Qdrant 或 Milvus。
- 保留 PDF 作为真实原始入口，先在 RAGFlow 解析，再由人工审核关键规则。
- 将课程、FAQ、收费与服务规则按知识域组织，避免所有内容混成一个无边界的大文档。
- 通过独立测试 Dataset 对比 256、384 和 512 等切块参数，再决定正式库配置。
- 在 uPil 代码中封装 RAGFlow Adapter，不让业务智能体直接依赖 RAGFlow 的页面或内部实现。

### 不足以支撑生产的做法

- 只使用默认 General 配置，不验证标题、表格和规则边界。
- 让大模型直接根据检索片段回答课时、余额、退费和班级名额。
- 没有知识版本、审核状态、来源引用和失败样本回流。
- 只展示一次“连接测试成功”，没有离线评测和回归结果。

结论：RAGFlow 不是低技术方案；把它当作黑盒问答插件才会显得技术含量不足。答辩中应展示至少一组基线与优化对比，以及一次从用户问题、Supervisor 路由、检索片段、工具调用到最终 SSE 回复的完整链路。
## 8. pytest 运行产物为什么集中存放

Windows 环境下，pytest 默认临时目录可能受到文件锁和权限影响。早期为隔离不同轮次的 SQLite 测试数据库，使用了多个独立的 `--basetemp` 目录，但这会使项目根目录逐渐堆积临时文件。项目现统一使用 `.test-artifacts/pytest/cache` 保存可再生缓存，并使用 `.test-artifacts/pytest/runtime` 保存当前测试的临时数据库。

该目录不属于源码和业务数据，必须被版本控制忽略。固定目录减少根目录污染，也便于 CI 清理和磁盘监控；如果并行测试或多任务执行产生目录竞争，CI 应为每个 Job 在 `.test-artifacts/pytest/jobs/<job-id>` 下分配独立子目录，而不是重新把随机目录放回项目根目录。

## 9. Git 仓库边界与密钥治理

uPil 主仓库只维护本项目编写的业务代码、测试、部署模板、审核后的知识库语料和工程文档。为了本地联调而下载的 RAGFlow 上游源码及其他参考仓库属于外部依赖，不复制其 `.git` 历史，也不作为嵌套仓库提交；依赖版本应通过文档、镜像标签或锁定的版本号描述。

真实 `.env`、数据库、日志、测试产物、自动备份和本机 Docker 客户端状态一律排除。`.env.example` 可以提交，但只能包含空值、占位符或明确标注为开发示例的非敏感默认值；生产环境不得沿用示例密码。首次提交和后续 CI 均应执行敏感信息扫描与大文件检查。

GitHub 身份验证与应用运行密钥采用不同的安全边界：GitHub 凭据只交给本机 Credential Manager 或浏览器授权；RAGFlow、LLM、MinIO、数据库和 A2A Token 由环境变量或 Secret Manager 注入。任何曾经出现在聊天、截图或日志中的真实密钥都按已泄露处理并立即轮换，不能仅依赖从 Git 中删除。
