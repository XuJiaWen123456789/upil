# 阶段 13-E：A2A 任务幂等、状态存储与基础可观测性

## 1. 阶段目标

本阶段在阶段 13-D 的跨进程 HTTP A2A 风格调用之上，补充任务治理能力：

- 使用 `task_id` 防止客户端重试造成同一任务重复执行；
- 使用任务内容指纹阻止同一个 ID 被不同任务内容复用；
- 提供任务结果查询和脱敏计数指标；
- 通过 TTL 与容量上限控制内存占用；
- 用自动化测试验证网络超时后“服务端已完成、客户端重试”的场景。

## 2. 实现范围

新增进程内任务仓库：

```text
D:/uPil/backend/app/a2a/task_store.py
```

核心接口：

- `execute(task, processor)`：首次执行或返回幂等缓存；
- `get(task_id)`：查询未过期的任务结果；
- `metrics()`：返回不含业务正文的计数；
- `clear()`：本地测试清理。

独立子服务新增接口：

```text
POST /internal/a2a/tasks
GET  /internal/a2a/tasks/{task_id}
GET  /internal/a2a/metrics
```

三个内部端点都要求 `X-A2A-Service-Token`，并且只在 `development`、`test`、`local`
环境开放。正式环境返回 404，避免把 Mock 子服务误暴露为生产能力。

## 3. 幂等语义

### 3.1 相同任务重复提交

客户端因网络超时重试时，必须复用第一次请求的 `task_id`。服务端计算规范化 JSON 的
SHA-256 指纹：

```text
相同 task_id + 相同任务指纹 -> 返回第一次结果，不重复执行
相同 task_id + 不同任务指纹 -> HTTP 409，不覆盖原结果
```

因此，HTTP 客户端的有限重试与服务端的幂等仓库形成配合：即使第一次任务已经执行，
但响应在网络中丢失，重试也只会命中已保存的结果。

### 3.2 任务 ID 的边界

`task_id` 是幂等键，不是认证凭据，也不能替代用户身份核验。认证仍由服务令牌和上游
身份系统负责。任务内容中的学员引用仍是脱敏值，仓库的指标不保存输入快照。

## 4. 状态治理

当前使用线程安全的进程内仓库，默认配置为：

```ini
A2A_LEARNING_TASK_TTL_SECONDS=1800
A2A_LEARNING_TASK_MAX_ENTRIES=1000
```

TTL 到期后任务结果不可查询；超过容量时淘汰最早更新时间的任务。重复查询会刷新
更新时间，避免正在使用的缓存被不必要地淘汰。

## 5. 基础指标

指标只返回以下计数，不返回问题正文、学员 ID、Artifact 正文、令牌或原始请求：

```json
{
  "received": 0,
  "executed": 0,
  "deduplicated": 0,
  "conflicts": 0,
  "completed": 0,
  "failed": 0,
  "stored": 0
}
```

这些计数可用于本地演示和故障定位，但还不是完整生产监控。生产环境应接入统一指标
系统、日志平台和链路追踪系统，并对指标端点增加更严格的运维访问控制。

## 7. 生产化替换计划

进程内仓库只适合单实例开发、测试和答辩演示。多实例生产部署时，必须替换为 Redis
或 PostgreSQL，并使用原子写入/唯一约束保证同一 `task_id` 的并发幂等。还需要补充：

- 任务状态持久化与恢复；
- 任务取消和人工接管；
- 更细粒度的状态流转事件；
- 统一监控告警；
- TLS/mTLS 或网关级服务身份；
- Artifact 大内容进入受控对象存储，只在任务结果中返回短期引用。

当前仍未接入真实 DSH、真实教务系统或真实生产数据。
