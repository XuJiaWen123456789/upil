# 阶段 13-F：DSH 受控执行门禁与适配器边界

## 1. 阶段定位

阶段 13-E 已完成 A2A 任务幂等、结果查询和基础指标。本阶段不直接接入真实
DeepSeekHarness，而是先把 DSH 作为“可替换执行器”放在明确的安全边界之后。

原因是 DSH 如果具备编写或执行分析脚本的能力，风险明显高于普通 FAQ 模型：它可能
接触学情数据、生成代码、访问文件或网络。先定义门禁和失败策略，可以避免为了答辩
展示而开放任意代码执行。

## 2. 当前项目中的职责

本项目第二个智能体是“学情分析智能体”，不是报表智能体。当前允许的 DSH 技能只有：

```text
learning_summary
```

输出格式只有：

```text
markdown_report
```

报表生成、任意 Python/Shell/SQL、文件读写、外部网络访问和数据库直连均不属于本阶段
能力范围。以后如确有运营报表需求，应新增独立技能、独立权限和独立数据出站策略，
不能复用学情分析技能绕过门禁。

## 3. 执行链路

```text
主系统权限校验
    -> 结构化学情快照
    -> A2A Task 严格协议校验
    -> DshExecutionGate 白名单门禁
    -> 真实 DSH 适配器（当前未配置）
    -> A2A Result 校验
    -> LangGraph 整理或安全降级
```

门禁输出的 `DshExecutionPlan` 只包含 task_id、协议版本、skill、超时和输出格式，
不包含 learner_ref、学员姓名、课程名称、原始问题或学情快照。

## 4. 默认关闭与 fail-closed

当前新增 `DisabledDshHarness` 仅用于验证适配器契约。调用结果明确为失败：

- 不执行任何代码；
- 不伪造“DSH 已完成”；
- 不允许自动重试业务失败；
- 标记 `handoff_required=true`，交给可信回退或人工流程。

这样即使未来 DSH 配置缺失、鉴权失败或沙箱未启动，也不会把不可验证的结果包装成
客服事实。阶段 13-F 的适配器尚未接入主 LangGraph 运行链路，现有 `mock` 和
`local_http` A2A 模式行为保持不变。

## 5. 真实 DSH 接入前的硬性条件

在允许真实执行器进入运行链路前，至少需要完成：

1. 独立进程或容器隔离，禁止访问主 API 的 Docker Socket；
2. 只读、最小化、脱敏数据输入，不允许 DSH 直接查询 PostgreSQL、RAGFlow 或 MinIO；
3. 禁止外部网络，或通过显式域名白名单和网络策略控制；
4. 临时工作目录、CPU、内存、进程数和运行时长均设置上限；
5. 禁止 Shell、危险 Python 模块、任意文件路径和动态安装依赖；
6. 输出必须再次通过 A2A 协议、Artifact 内容和隐私安全校验；
7. 服务身份使用短期凭据或 mTLS，不能只依赖固定共享 Token；
8. 生产环境增加审计、告警、人工接管和任务取消能力。

## 6. 当前验证结果

新增：

```text
D:/uPil/backend/app/a2a/dsh_harness.py
D:/uPil/tests/test_dsh_harness.py
```

覆盖合法计划生成、安全开关拒绝、非白名单技能拒绝、敏感字段不进入计划，以及 DSH
未配置时的安全失败。当前只使用虚构演示数据。

## 7. 答辩口径

> 我没有把 DSH 当成一个可以执行任意代码的黑盒直接接入客服。项目先通过 A2A Task
> 和执行门禁限制技能、输出格式、运行时长、外部网络和副作用，并且只把脱敏结构化
> 输入交给未来的 DSH 适配器。当前真实 DSH 尚未配置，系统采用 fail-closed，宁可转
> 可信回退或人工，也不伪造分析结果。这样既体现了 DSH 在复杂学情分析中的扩展价值，
> 又把代码执行风险控制在可审计边界内。

当前不能表述为“已接入真实 DeepSeekHarness”或“已实现生产级代码沙箱”。
