# 阶段 14-E：教师媒体双人复核与细粒度权限

> **历史方案说明：** 该能力曾于阶段 14-E 实现，现已因项目产品边界收缩下线。本文仅保留设计过程记录，不代表当前可用功能。

## 1. 阶段目标

在只保留家长和教师两类业务角色的前提下，把“上传机构教学素材”和“批准素材对家长开放”拆成两项独立职责。教师上传的图片先进入 `pending`，必须由另一名具有复核权限的教师批准后，才能按照可见范围生成短时访问地址。

本阶段不增加管理员、校区运营或独立审核员角色，避免把 uPil 扩展成通用内容管理后台。

## 2. 为什么上传素材不能直接公开

教师上传内容可能包含学员作品、教师肖像、课堂环境、错误课程信息或未经授权的素材。若上传即公开，单个账号误操作或被盗后可以直接向家长发布内容，无法形成有效的事前控制。

双人复核把风险拆成两个独立动作：

1. 上传者负责文件来源、标题、替代文本和可见范围；
2. 复核者确认内容、授权和发布范围；
3. 系统记录双方身份、审核时间和审核意见；
4. 只有 `approved` 素材可以按业务可见范围对家长或教师开放。

## 3. 为什么不增加 reviewer 业务角色

家长和教师描述的是稳定业务身份，上传和复核描述的是教师内部岗位职责。若每增加一个动作就增加角色，会快速形成 `teacher_uploader`、`teacher_reviewer`、`teacher_lead` 等角色膨胀。

因此本项目采用“角色 + 权限点 + 资源规则”：

| 控制维度 | 示例 | 作用 |
| --- | --- | --- |
| 业务角色 | `parent`、`teacher` | 确定用户所属业务人群 |
| 权限点 | `media_upload`、`media_review` | 确定教师可执行的动作 |
| 资源规则 | `uploaded_by != reviewer_id` | 防止同一人完成上传和批准 |
| 状态规则 | 仅 `pending` 可审核 | 防止普通接口覆盖既有审核结论 |

## 4. 数据模型

### 4.1 `user_permissions`

联合主键为 `(user_id, permission)`，同一用户不会重复获得同一权限。权限名称使用服务端白名单，当前只识别：

- `media_upload`：上传机构媒体；
- `media_review`：复核待审机构媒体。

外部 JWT Claim、HTTP Header 和请求体中的权限字符串均不参与授权。

### 4.2 `media_assets` 审核轨迹

新增字段：

- `uploaded_by`：服务端根据认证上下文写入的上传教师；
- `reviewed_by`：作出批准或拒绝结论的教师；
- `reviewed_at`：审核发生时间；
- `review_comment`：受长度限制的审核意见。

迁移前历史素材可能没有 `uploaded_by`。由于系统无法证明其上传者，普通审核接口会返回 409，要求先进入人工数据治理流程，而不是为了兼容旧数据放宽职责分离。

## 5. 状态机与访问规则

```text
教师上传
   │
   ▼
pending ──另一名复核教师批准──> approved ──按 visibility 访问
   │
   └────另一名复核教师拒绝──> rejected ──所有业务角色禁止访问
```

- `pending`：仅上传者和具有 `media_review` 权限的教师可以读取原件；
- `approved`：家长只能读取 `public_faq`，教师可以读取 `public_faq` 和 `internal_staff`；
- `rejected`：所有家长和教师都不能生成访问地址；
- 已经批准或拒绝的素材不能通过普通审核接口再次修改，重复请求返回 409；
- 即使同一教师同时具有 `media_upload` 和 `media_review`，只要 `uploaded_by` 等于当前用户，仍返回 403。

## 6. 认证与授权边界

OIDC/JWT 或可信代理 Header 只证明“当前用户是谁”。uPil 在身份映射成功后，从本地 `users` 和 `user_permissions` 加载角色、校区范围和动作权限。

这样设计可以避免：

- 客户端伪造 `permissions` Header；
- JWT 被错误签发高权限 Claim 后直接控制业务数据库；
- 旧版本应用把未来新增权限名误解释为有效能力；
- 权限数据库故障时静默降级并错误放行。

权限查询异常统一返回脱敏 503，并记录固定原因码，不记录数据库 DSN、凭据或异常正文。

## 7. 并发审核控制

PostgreSQL 审核查询使用 `SELECT ... FOR UPDATE` 锁定目标媒体行。两名复核教师同时提交时，第二个事务会等待第一个事务结束，然后重新看到最新状态；由于只有 `pending` 可以迁移，第二次提交返回 409，避免后写覆盖先写。

数据库行锁只解决同一媒体记录的并发写冲突，不代替接口幂等键、请求超时治理或跨服务分布式事务。

## 8. MinIO 与关系数据库的一致性

媒体原文件写入 MinIO，元数据和审核轨迹写入关系数据库，两者不属于同一个本地事务。当前上传流程采用补偿机制：MinIO 上传成功但数据库提交失败时，尽力删除刚写入的对象并返回 503。

该补偿仍可能因对象存储故障而失败。生产增强方案包括：

1. 通过 outbox 记录待删除或待确认对象；
2. 后台任务重试补偿动作；
3. 定期对账 MinIO 对象键与 `media_assets`；
4. 对孤儿对象设置隔离区和生命周期清理策略；
5. 对发布和撤回操作增加幂等键。

## 9. 审计与隐私

完整审核意见只保存在受控媒体业务表中。结构化审计日志记录审核状态和“是否填写意见”，不复制自由文本，避免包含姓名、联系方式或争议描述的内容扩散到日志、监控和告警平台。

数据库外键使用 `SET NULL` 保留媒体历史记录。人员账号删除或脱敏后，媒体记录仍可保留审核时间和结论；若业务要求不可抵赖审计，应采用账号停用、审计快照或独立不可变审计存储，而不是物理删除用户。

## 10. 测试与验证

自动化测试覆盖：

- 家长、普通教师不能上传或审核；
- 上传人由服务端认证上下文写入；
- 同时拥有上传和审核权限的教师仍不能审核自己上传的素材；
- 独立复核教师可以访问 pending 并批准或拒绝；
- 审核人、审核时间和审核意见正确落库；
- approved 按可见范围开放，rejected 禁止访问；
- 已完成审核的素材不能被第二次覆盖；
- Header 和 JWT 中伪造的权限无效；
- 未知数据库权限不会进入授权上下文；
- 权限数据库故障返回脱敏 503；
- 超过 500 字的审核意见在 HTTP 契约层返回 422；
- 媒体复核权限不会扩大教师班级和学员访问范围。

## 11. 尚未完成的生产能力

本阶段完成了业务职责分离和可审计状态流，但不能宣称已经完成完整媒体安全平台。仍需补充：

- 恶意文件和病毒扫描；
- 图片涉敏、违规和内容安全检测；
- 版权、肖像和学员作品授权证明管理；
- 已发布素材撤回、修订和重新审核流程；
- 对象存储与数据库的 outbox、重试和定期对账；
- 审核队列、通知、超时 SLA 和积压告警；
- 生产权限申请、审批、回收和定期复核流程。

## 12. 阶段结论

uPil 在不增加后台业务角色的情况下，通过教师细粒度权限、上传者不可自审、一次性状态迁移、数据库行锁和审核轨迹，实现了可验证的媒体双人复核边界。它仍然是智能客服与学情助手的配套内容安全能力，而不是校区管理后台。
