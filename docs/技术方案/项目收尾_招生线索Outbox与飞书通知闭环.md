# 招生线索 Outbox 与飞书通知闭环

## 1. 目标与边界

本功能解决的是“中高意向线索已经进入 uPil，但顾问没有持续打开页面时如何及时获知”。
飞书是提醒渠道，不承担线索领取、联系方式解密、跟进记录或状态迁移。

完整链路：

```text
家长对话 -> 意向旁路 -> 确定性状态机 -> 线索与 Outbox 同事务落库
         -> 后台派发器 -> 飞书低敏提醒 -> 顾问回 uPil 领取和跟进
```

## 2. 为什么不在线索事务里直接请求飞书

若数据库事务中直接调用 Webhook，第三方超时会延长数据库事务并拖慢家长回复；
请求失败还会造成“线索是否应该回滚”的错误耦合。Transactional Outbox 让线索和待
通知事件原子落库，网络请求在提交后执行，因此第三方故障不会破坏核心业务事实。

个人作品项目暂不引入 Kafka、RabbitMQ 或 Celery。当前通知规模较小，PostgreSQL
Outbox 加应用内轮询已经覆盖持久化、重试、崩溃恢复和多实例领取，运维成本更合适。

## 3. 事件与幂等

首期事件：

- `medium_intent_created`：中意向首次形成，仅当阈值配置为 `medium` 时生成；
- `high_intent_waiting_contact`：高意向首次形成，但联系方式尚未授权；
- `contact_authorized`：联系方式首次完成明确授权并加密保存。

唯一键为 `lead_id + event_type + channel + intent_version`。重复表达相同意向不会重复
建事件；并发插入由数据库唯一约束和保存点共同收敛，通知冲突不能回滚线索事务。

## 4. 投递与补偿

后台任务按批次领取 `pending`、已到期 `retry`，以及超过五分钟的遗留 `sending` 事件。
投递成功标记 `sent`；失败只保存稳定错误码，按线性退避重试，达到上限后标记 `failed`。
第三方响应正文、Webhook 和异常详情不会写入数据库或日志。

该方案提供至少一次投递。若飞书已成功但进程在标记 `sent` 前崩溃，提醒可能重复；
顾问领取和跟进仍受 uPil 数据库状态机约束，因此重复提醒不会产生重复业务操作。

## 5. 隐私与权限

外部消息只包含课程名称、试听或报名意向、联系方式是否授权和顾问工作台入口。禁止
发送明文手机号、邮箱、家长原话、完整对话、家长/学员内部编号、密文、指纹和对象键。
顾问必须登录 uPil、具备 `lead_followup` 权限并领取线索后，才能查看已授权联系方式。

## 6. 配置与发布

默认 `LEAD_NOTIFICATION_ENABLED=false`。启用前必须执行迁移
`009_add_lead_notification_outbox.sql`，并通过 Secret 注入 `FEISHU_WEBHOOK_URL`。
生产 Webhook 和顾问入口必须使用 HTTPS。健康探针只返回 `disabled` 或 `configured`，
不会向飞书发送测试消息，也不会返回任何地址。
