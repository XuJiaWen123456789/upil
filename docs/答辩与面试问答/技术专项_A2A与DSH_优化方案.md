# 技术专项：A2A 协议与 DeepSeek Harness（DSH）优化方案

> 版本：v2.0
>
> 定位：uPil 的架构决策与答辩准备资料。
>
> 说明：本文将 DSH 理解为“以 DeepSeek 等大模型为核心，封装代码生成、工具调用、沙箱执行和产物管理能力的 Harness 运行时”。如果最终采用某个具体项目，应在实现阶段锁定仓库地址、版本号、许可证和实际 API，不把本文抽象能力描述当成第三方产品的既有承诺。

## 一、最终结论

### 1. A2A 对整个 uPil 不是全面提升，对学情分析智能体是显著提升

A2A 不会直接提高 FAQ 的回答准确率，也不会替代 LangGraph 的流程编排。它的价值集中在：把需要独立运行、异步处理、沙箱执行和独立审计的学情分析智能体，变成可治理的远程智能体服务。

| 场景 | 是否使用 A2A | 原因 |
| --- | --- | --- |
| 课程、校区、请假、调课等 FAQ | 否 | 低延迟、流程简单，进程内调用更合适 |
| 个人课时和出勤查询 | 默认否 | 主要是权限过滤和确定性查询，不需要远程智能体 |
| 固定口径的出勤统计 | 默认否 | 可由参数化 SQL 或固定报表服务稳定完成 |
| 自定义学情统计、复杂分析、运营报表 | 是，作为二期能力 | 需要任务生命周期、异步执行、独立资源和执行产物 |

因此，A2A 在整个项目中的必要性属于中等，在 DSH 驱动的学情分析服务中的必要性较高。这个边界比让所有请求都走 A2A 更合理。

### 2. 学情分析智能体是第二个业务智能体，报表只是它的输出形式

uPil 的核心业务智能体收敛为两个：FAQ 智能体负责规则和课程知识问答；学情分析智能体负责课时、消课、出勤、缺勤、班级对比和趋势分析。报表不是独立智能体，而是学情分析智能体把分析结果组织成 Markdown、JSON 或 CSV 的一种输出方式。

DSH 更适合放在学情分析智能体内部，承担受控的分析执行能力。对外暴露的是业务语义明确的 Learning Analysis Agent，而不是让 Supervisor 把任意自然语言和数据库权限直接交给 DSH。

推荐关系：

~~~text
浏览器
  ↓ SSE
FastAPI Gateway
  ↓
LangGraph Supervisor
  ├── FAQ Agent（课程规则与机构知识）
  └── 学情分析智能体（Learning Analysis Agent）
        ↓ A2A Task（复杂/长耗时任务时启用）
      DSH Runtime（最小权限沙箱，可选执行器）
        ↓
      Markdown/JSON/CSV 报表 Artifact
~~~

核心区分是：A2A 是智能体之间的通信协议，学情分析智能体是业务角色，DSH 是它内部可替换的执行运行时；三者不是同一层技术。

## 二、重新定义两个技术点的职责

### 1. A2A 的职责

A2A 只负责跨智能体协作边界，不负责：

- 数据库表设计；
- 替代行级权限控制；
- 保证模型生成代码正确；
- 把所有工具调用都变成远程调用；
- 取代 LangGraph 的状态机和重试逻辑。

在 uPil 中，A2A 的职责是传递结构化学情分析任务、跟踪任务状态、传递结果 Artifact，并让 Supervisor 能够处理超时、失败、重试和人工兜底。

### 2. DSH 的职责

DSH 可以承担：

- 将受控任务转成分析步骤或预置分析模板；
- 在隔离环境中执行 Python 数据处理代码；
- 生成统计结果和 Markdown 报表；
- 输出执行日志、代码版本、模板版本和结果文件等 Artifact；
- 在超时、依赖错误、数据格式错误时返回可识别的失败状态。

DSH 不应承担：

- 直接修改排课、考勤、收费等业务数据；
- 使用管理员数据库账号；
- 自由访问互联网并安装任意依赖；
- 输出手机号、身份证号等原始敏感字段；
- 自己决定用户能查看哪些校区、班级和学员。

## 三、三档落地策略

### 第 1 档：确定性报表模板，作为 MVP 和生产默认路径

适用于“本月完课率”“缺勤 TOP5”“某班出勤汇总”等固定需求。

~~~text
自然语言
  ↓
Supervisor 提取结构化参数
  ↓
权限服务校验用户范围
  ↓
参数化 SQL 查询
  ↓
确定性 Python 聚合
  ↓
统一格式化报表
~~~

这一档不需要 DSH，也不需要远程 A2A。它保证口径一致、易测试、低延迟，是一期必须先做好的主链路。

### 第 2 档：A2A + 学情分析智能体 + DSH 受控分析，作为项目亮点和二期能力

适用于多条件交叉分析、近三个月趋势对比、运营分析报告等任务。

推荐做法：

1. Supervisor 只提取 analysis_type、时间范围、班级范围和指标列表；
2. 学情分析智能体再次进行角色、校区、班级和数据字段校验；
3. 数据访问层使用只读、参数化查询获取最小数据集；
4. 对姓名使用内部学员编号或脱敏名称，手机号等字段直接不下发；
5. DSH 在沙箱中执行分析；
6. 返回 JSON 指标、Markdown 报表和执行轨迹 Artifact；
7. Supervisor 对结果进行数值、隐私和业务规则校验；
8. 失败重试有限次数，仍失败则转人工。

这一档体现“自然语言任务理解 + 确定性数据治理 + 隔离式智能执行 + 可审计结果”的完整链路。最终产出可以是自然语言摘要，也可以是运营报表，但业务智能体始终是学情分析智能体。

### 第 3 档：完全自由的自动编程分析，不纳入一期

让模型任意生成 SQL、安装依赖、访问生产库并执行脚本，风险和验证成本过高，不适合作为教育机构客服系统的默认方案。

只有在具备独立分析数据仓库、完整容器隔离、SQL AST 校验、命令白名单、脱敏、审计、人工审批和回归评估后，才考虑扩大范围。

## 四、建议的报表任务结构

下面是业务层的稳定契约，映射到 A2A 的字段时，应以最终采用的 A2A 版本和 SDK 为准。

~~~json
{
  "task_id": "rt_20260901_0001",
  "task_type": "class_attendance_analysis",
  "requester": {
    "user_id": "U1001",
    "role": "operator",
    "campus_ids": ["C01"]
  },
  "scope": {
    "class_id": "CLASS_DANCE_01",
    "period_start": "2026-08-01",
    "period_end": "2026-08-31"
  },
  "metrics": ["completion_rate", "absence_top5"],
  "output_format": "markdown_report",
  "data_policy": {
    "read_only": true,
    "mask_student_name": true,
    "exclude_sensitive_fields": true
  },
  "template_version": "attendance-report-v1"
}
~~~

不建议直接传递“请自由分析数据库并生成任意脚本”这类自由文本任务。结构化任务可校验参数、复核权限、重放任务和审计结果。

## 五、用户示例的优化流程

用户提问：

> 帮我统计一下这个月舞蹈班级的学员完课率、缺勤 TOP5，输出一份运营报表。

### 1. Supervisor

- 判断为数据统计任务；
- 提取“舞蹈班级”“本月”“完课率”“缺勤 TOP5”“运营报表”；
- 不自行扩大为全校范围；
- 生成内部 ReportRequest。

### 2. 权限与数据层

- 根据当前用户身份确认可访问校区和班级；
- 使用参数化 SQL 获取必要字段；
- 使用只读连接，禁止 DSH 直接拿生产库超级权限；
- 生成一次性、最小化的数据快照。

### 3. A2A 学情分析智能体

- 将 LearningAnalysisRequest 映射为 A2A Task；
- 记录任务状态、调用方、模板版本和超时配置；
- 处理 working、completed、failed 等状态；
- 长任务采用异步等待或状态更新，不阻塞普通客服请求。

### 4. 学情分析智能体内部的 DSH 执行器

- 优先匹配 attendance-analysis-v1 模板；
- 在沙箱中完成聚合和报表排版；
- 禁止修改业务数据；
- 返回结果数据、Markdown 报表和执行轨迹。

### 5. 结果校验与客服表达

- 检查完课率是否在 0% 到 100% 之间；
- 检查 TOP5 是否超过实际缺勤人数；
- 检查手机号、身份证号等敏感字段；
- 校验通过后转换成用户能理解的话术；
- 失败则有限重试，最终转人工并保留任务编号。

## 六、A2A 的项目价值

### 价值一：隔离高风险执行能力

客服问答主要是检索和查询，报表分析可能触发代码执行。通过独立 Report Agent 和 A2A 边界，可以把代码执行放入受控环境，降低单个组件故障影响主客服服务的风险。

### 价值二：把回答升级为可追踪任务

FAQ 是一次请求一次响应；报表生成可能需要排队、执行、重试和产出文件。Task 和 Artifact 语义更适合表达这个过程，可以记录输入、状态、结果和失败原因。

### 价值三：支持独立扩缩容和替换

客服问答强调低延迟，报表分析可能消耗 CPU、内存和执行时间。两者独立部署后可以分别扩容；以后替换 DSH，Supervisor 仍可面对稳定的 Report Agent 契约。

### 价值四：体现工程化而不是简单调用模型

LangGraph 负责编排，A2A 负责智能体服务间协作，DSH 负责受控执行，PostgreSQL 负责事实数据，RAGFlow 负责知识检索。不同组件按风险、时延和数据特征划分职责。

### 必须诚实说明的边界

不能说“用了 A2A 所以准确率自动提高”或“用了 DSH 所以代码一定安全”。准确率来自数据口径、权限过滤、模板和校验；安全来自沙箱、白名单、最小权限和审计。A2A 主要提升服务解耦、任务治理和跨智能体协作能力。

## 七、答辩高频问答

### Q1：为什么不是所有 Agent 都使用 A2A？

**答：** A2A 解决跨服务智能体协作，不是普通函数调用的替代品。FAQ 和学情查询对延迟敏感、执行链路短，放在 LangGraph 进程内更高效。只有报表任务需要独立资源、异步状态、沙箱和可审计 Artifact，才跨 A2A 边界。

### Q2：A2A 对本项目到底有多大提升？

**答：** 对普通客服问答提升有限，对报表智能体提升明显。它不直接提高回答质量，但让高风险、长耗时的分析能力可以独立部署、隔离执行、跟踪任务和返回产物。我们让它只出现在确实需要智能体协作的边界上。

### Q3：A2A 和 MCP 如何区分？

**答：** MCP 更适合连接智能体和工具，例如检索知识库或调用查询接口；A2A 更适合连接两个具有任务处理能力的智能体服务。uPil 中 RAGFlow 是知识检索能力，Supervisor 调度独立 Report Agent 则适合 A2A。

### Q4：为什么不让 DSH 直接连接 PostgreSQL？

**答：** DSH 包含模型生成和代码执行能力，不应拥有生产数据库的广泛权限。系统先通过权限服务和参数化 SQL 获得最小化、脱敏的数据快照，再交给 DSH 只读分析，从而分离数据权限与代码执行权限。

### Q5：为什么不让大模型自由生成 SQL 和 Python？

**答：** 教育机构客服要求结果稳定和可解释。自由生成代码可能造成统计口径不一致、漏掉班级权限条件或泄露字段。MVP 采用预置报表模板和参数化查询；DSH 只在受控快照上分析，并经过数值和隐私校验。

### Q6：DSH 如果只是模型 API 的一层封装，价值还大吗？

**答：** 如果 DSH 只有模型调用封装，价值有限，不能仅因名称就引入。它至少需要提供可验证的执行隔离、工具白名单、超时取消、日志和产物管理能力；否则使用 LangGraph 节点或普通任务服务更合适。采用条件是 DSH 能提供受控执行能力，而不是项目必须使用 DSH。

### Q7：A2A 调用失败怎么办？

**答：** Supervisor 设置连接超时、任务超时和有限重试；Report Agent 返回结构化失败原因；结果层检查数值边界、数据范围和隐私；超过重试次数后转人工。普通 FAQ 不依赖 DSH，因此 DSH 故障不会拖垮基础客服能力。

### Q8：一期没有完整部署远程 DSH，如何说明？

**答：** 一期先完成确定性 FAQ、权限查询和固定报表模板，建立数据和安全基础。随后用本地适配器验证 Report Agent 任务契约，再把同一契约替换为远程 A2A 服务。这样是渐进式实现，避免在数据库和权限模型尚未稳定时先搭建自由编码系统。

## 八、技术栈与边界

| 层次 | 推荐技术 | 职责 |
| --- | --- | --- |
| API 网关 | FastAPI | 鉴权、校验、SSE、错误处理 |
| 对话编排 | LangGraph | Supervisor、状态机、路由、重试、人工兜底 |
| 知识检索 | RAGFlow | 课程制度、客服 FAQ 等非结构化知识 |
| 事实数据 | PostgreSQL | 用户、学员、班级、课时、出勤等结构化数据 |
| 跨智能体通信 | A2A | Supervisor 与独立 Report Agent 的任务协作 |
| 分析执行 | DSH | 受控分析规划、沙箱执行和报表产物生成 |
| 浏览器传输 | SSE | 向用户推送回答和任务状态 |
| 运行隔离 | Docker/容器沙箱 | 限制 CPU、内存、网络、文件系统和时间 |

前端 SSE 与 A2A 不是重复技术：前者面向浏览器用户体验，后者面向后端智能体服务协作。

## 九、实施阶段

1. **阶段 2：数据库与权限基础**：建立用户、角色、校区、学员、班级、课时、出勤表；预留 report_task、report_artifact、audit_log。
2. **阶段 3：RAGFlow 知识库**：导入课程规则和客服 FAQ；建立引用来源、知识版本和低置信度转人工。
3. **阶段 4：确定性报表服务**：实现完课率、缺勤 TOP5 模板；添加口径、边界值和权限回归测试；进程内模拟 Report Agent。
4. **阶段 5：DSH 执行器验证**：验证隔离、资源限制、工具白名单和 Artifact；只使用脱敏快照，不连接生产库；不满足安全条件时保留确定性报表服务。
5. **阶段 6：A2A 远程化**：增加 Agent Card 和 Task 适配；实现状态同步、超时、重试、取消和人工兜底；进行故障注入和端到端审计验证。

## 十、验证指标

- 固定报表结果与基准 SQL 的一致率；
- 越权查询拦截率；
- 敏感字段输出拦截率；
- 报表任务成功率和 P95 完成时间；
- DSH 超时、失败和重试比例；
- A2A 故障时 FAQ 可用性；
- 是否能根据 task_id 回放输入、模板版本和 Artifact；
- 是否能阻止超时脚本和异常内存消耗。

## 十一、本轮最终架构决策

~~~text
一期默认：
FastAPI + SSE + LangGraph + PostgreSQL + RAGFlow
固定报表：参数化 SQL/Python，进程内执行

二期亮点：
Report Agent 独立部署
Report Agent 通过 A2A 接收结构化任务
Report Agent 内部按条件调用 DSH
DSH 只处理脱敏快照，输出可审计 Artifact

明确不做：
让 DSH 直接访问生产库
让模型任意执行系统命令
让所有客服请求强制经过 A2A
把协议名称当作准确率和安全性的自动保证
~~~
