# Transactional Outbox 与飞书通知面试问答

## Q1：为什么有线索池还要增加飞书通知？

线索池负责完整业务状态，适合领取、查看授权联系方式和记录跟进；飞书负责及时提醒。
只用页面容易漏看，只用飞书又无法可靠承载权限、审计和状态迁移，因此两者分工而非替代。

## Q2：为什么不能保存线索后直接调用飞书 Webhook？

数据库提交和 HTTP 请求无法构成同一个本地事务。先发飞书再提交可能出现提醒存在但线索
不存在；先提交再发送可能在进程崩溃时漏通知。Outbox 与线索同事务保存，后台再投递，
把核心事实的一致性和外部渠道的最终送达拆开处理。

## Q3：Outbox 如何保证不丢事件？

线索更新和 Outbox 事件共享一个 PostgreSQL commit，任一失败都会共同回滚。提交成功后，
事件会一直保持 `pending/retry`，应用重启后仍能继续领取，不依赖进程内内存。

## Q4：是否能保证飞书绝对不重复？

不能宣称 exactly-once。Webhook 成功后、数据库标记 `sent` 前若进程崩溃，补偿任务可能
再次发送。系统通过事件唯一键避免业务侧重复建事件，通过 uPil 领取与跟进状态机保证
重复提醒不产生重复操作，这属于至少一次投递下的业务幂等。

## Q5：为什么不使用消息队列？

当前是个人项目，通知吞吐低，PostgreSQL 已是核心依赖。直接引入 Kafka 或 RabbitMQ 会
增加部署、监控和故障恢复成本，却没有相应规模收益。若未来通知量、渠道数或消费者数
显著增加，可保留 Outbox 并由 CDC/Relay 发布到消息队列，不需要修改线索事务边界。

## Q6：如何避免把家长隐私发到群里？

Outbox 使用受控字段白名单，不保存消息原文、用户编号或联系方式。飞书只显示课程、意向
和授权状态，真实联系方式继续以 Fernet 密文保存在 PostgreSQL，顾问回系统鉴权后查看。

## Q7：飞书不可用会影响家长聊天吗？

不会。家长请求只提交线索和 Outbox，不访问飞书；后台派发失败后单独重试，达到上限标记
失败。通知渠道故障不回滚线索，也不延长聊天请求的网络等待时间。

## Q8：多实例如何避免同时发送同一条事件？

领取时使用数据库行锁和 `SKIP LOCKED`，先把事件提交为 `sending` 再执行网络请求。超过
五分钟的遗留 `sending` 可重新领取，用于进程中断恢复。业务上接受极小概率重复提醒。
