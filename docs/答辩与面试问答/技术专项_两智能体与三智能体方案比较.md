# uPil 智能体数量方案比较与最终决策

## 一、问题定义

当前有两种候选设计：

- 两智能体：FAQ 智能体 + 学情分析智能体；
- 三智能体：Supervisor 主控智能体 + FAQ 智能体 + 学情分析智能体。

本方案不把报表单独定义为智能体。完课率、缺勤 TOP5、趋势分析和运营报表，都是学情数据分析的不同指标或输出形式。

## 一、本轮重新判断：最佳方案

### 结论

本项目建议采用：**逻辑上的三智能体，工程上的单体起步，业务上的两个领域智能体**。

具体划分如下：

1. **Supervisor 主控智能体**：负责理解用户请求、提取任务参数、路由、权限前置检查、结果校验、重试和人工兜底。
2. **FAQ 知识问答智能体**：负责课程规则、请假调课、补课、装备、校区政策和活动说明等非结构化知识问答。
3. **学情分析智能体**：负责课时、消课、出勤、缺勤、完课率、班级趋势和运营报表等结构化数据分析。

这里的“三智能体”是**职责上的三角色**，不表示一期就要部署三个独立进程。第一期三个角色运行在同一个 LangGraph 中，第二期再把学情分析能力服务化，第三期才在复杂任务上引入 A2A。这样既能体现多智能体架构的设计价值，又不会因为过早分布式部署而增加调试、鉴权和运维成本。

Supervisor 在实现上应保持轻量。它可以使用大模型完成意图识别和参数提取，但不应直接执行 SQL、计算业务指标或绕过领域智能体访问数据库。这样可以把“编排”和“业务计算”分开，也便于在答辩中解释系统的安全边界。

### 为什么不是“FAQ + 学情”两个智能体直接结束

两智能体方案适合最小 MVP，开发成本最低，适合先验证 FAQ 检索和个人学情查询。但它会让路由、参数提取、权限前置检查、异常重试和人工转接分散在接口层或某个业务智能体中，后续接入 A2A、长任务和执行轨迹时边界不够清晰。

因此，项目可以在代码部署层面保持“两类业务智能体”，但在系统设计层面保留 Supervisor 这一独立控制角色。它不是为了增加数量，而是为了明确多智能体系统中的控制平面。

### 为什么不是“FAQ + 学情 + 报表”

报表不是独立业务领域，而是学情分析的一种输出形式。个人学情摘要、班级缺勤 TOP5、完课率趋势和 Markdown/CSV 报表都依赖相同的数据源、权限规则和统计口径。将报表单独拆出会重复实现权限和指标计算，并造成“统计到底归谁负责”的边界问题。

所以，报表应作为学情分析智能体的 output_format 或任务类型，而不是第三个业务智能体。

## 二、最终建议

推荐采用：逻辑上三智能体、部署上分阶段，业务上两个领域智能体。

角色划分：

~~~text
1. Supervisor 主控智能体
   负责意图识别、任务分类、参数提取、路由、重试、结果校验和人工兜底

2. FAQ 知识问答智能体
   负责课程、校区、装备、请假、调课、补课和活动等规则问答

3. 学情分析智能体
   负责个人课时、消课、出勤、缺勤、完课率、班级对比、趋势和运营报表
~~~

Supervisor 是多智能体系统的控制平面，另外两个是业务能力平面。把 Supervisor 明确为智能体角色，有利于体现 LangGraph 的编排价值；把报表归入学情分析，又能控制业务边界和智能体数量。

## 三、两智能体与三智能体对比

| 比较维度 | 两智能体：FAQ + 学情分析 | 三智能体：Supervisor + FAQ + 学情分析 |
| --- | --- | --- |
| 业务职责 | 简单清晰 | 清晰，控制职责独立 |
| LangGraph 展示效果 | 主要是节点路由 | 能展示监督、委派、结果回收和兜底 |
| 代码复杂度 | 较低 | 中等，需要统一状态和路由契约 |
| 适合一期开发 | 很适合 | 适合，但 Supervisor 初期应保持轻量 |
| 扩展复杂任务 | 需要在业务智能体内继续增加逻辑 | 更容易接入 RAGFlow、A2A 和 DSH |
| 权限治理 | 容易集中实现 | Supervisor 前置检查，领域智能体二次校验 |
| 答辩表达 | 容易解释，但多智能体亮点较弱 | 能解释为什么拆分以及各自边界 |
| 过度设计风险 | 低 | 中等，需要避免过度自主规划 |
| 综合推荐度 | 适合极简 MVP | 最适合本项目目标方案 |

## 四、为什么不采用“FAQ + 学情分析 + 报表”

这种三智能体划分看似数量更多，但业务边界不自然：

1. 报表是学情分析结果的展示方式，不是稳定的业务领域；
2. 个人出勤摘要和班级出勤报表都依赖课时、消课、出勤数据，拆开会重复权限和统计口径；
3. 报表智能体容易退化成文件生成器，职责过窄；
4. 加入趋势分析和异常缺勤后，很难判断功能应该归属报表智能体还是学情智能体；
5. 答辩时容易被追问：既然报表只是输出格式，为什么要单独拆成智能体？

更合理的设计是由学情分析智能体根据角色和任务类型输出不同结果：

| 用户 | 任务 | 输出 |
| --- | --- | --- |
| 家长 | 查询孩子课时和出勤 | 个人学情摘要 |
| 教师 | 查看班级缺勤情况 | 班级分析结果 |
| 运营人员 | 对比舞蹈班近三个月完课率 | 趋势分析 |
| 运营人员 | 输出本月缺勤 TOP5 | Markdown 或 CSV 运营报表 |

## 五、推荐架构

~~~text
                         ┌─────────────────────────┐
                         │  Supervisor 主控智能体   │
                         │ 意图识别/参数/路由/兜底   │
                         └──────────┬──────────────┘
                                    │
             ┌──────────────────────┴──────────────────────┐
             │                                             │
             ▼                                             ▼
┌─────────────────────────┐                   ┌─────────────────────────┐
│ FAQ 知识问答智能体       │                   │ 学情分析智能体           │
│ RAGFlow + 规则引用       │                   │ PostgreSQL + 指标计算    │
│ 课程与机构政策问答       │                   │ 课时/出勤/趋势/报表       │
└─────────────────────────┘                   └──────────┬──────────────┘
                                                         │
                                      复杂或长耗时任务时 │ A2A
                                                         ▼
                                      ┌─────────────────────────┐
                                      │ DSH 受控分析执行器       │
                                      │ 脱敏快照/沙箱/Artifact    │
                                      └─────────────────────────┘
~~~

DSH 不是第四个业务智能体，而是学情分析智能体内部的执行运行时；A2A 是 Supervisor 与独立学情分析服务之间的通信协议，二者属于不同层次。

## 六、职责边界

### Supervisor 主控智能体

负责判断 FAQ、学情分析或人工协助意图，从自然语言提取学员、班级、时间范围、指标和输出格式，组织结构化任务，选择进程内调用或 A2A 远程调用，处理超时、重试、结果校验和人工兜底。

不负责直接计算出勤率、直接判断最终数据权限、直接执行任意 SQL 或生成未经校验的最终数字。

### FAQ 知识问答智能体

负责检索 RAGFlow 中的课程、校区、装备和请假规则，给出带来源的解释，低置信度时转人工。不负责查询实时课时和出勤数据。

### 学情分析智能体

负责查询个人课时、消课和出勤，统计班级完课率、缺勤 TOP5 和趋势，根据角色执行数据范围校验，使用固定模板或受控 DSH 完成分析，输出自然语言摘要、JSON、Markdown 或 CSV。

不负责课程规则知识问答，不负责收费退费和修改排课考勤。

## 七、A2A 与 DSH 的最佳位置

### A2A

建议在 Supervisor 与独立学情分析智能体服务之间使用，而不是让每个节点都使用：

~~~text
Supervisor
    │
    ├── FAQ：低延迟任务，进程内调用
    │
    └── 学情分析：
          ├── 简单查询，进程内调用
          └── 复杂分析，A2A 调用独立服务
~~~

亮点是按任务风险和耗时选择通信方式，而不是为了使用协议强制远程化。

### DSH

DSH 只能接收已通过权限校验的数据快照、结构化分析任务、明确的指标和输出格式、模板版本或允许的工具集合。

DSH 不应接收生产数据库超级账号、未过滤的全量学员数据、无限制的自由分析 Prompt，或可修改业务数据的工具权限。

## 八、业务示例链路

用户请求：

> 帮我统计一下这个月舞蹈班级的学员完课率、缺勤 TOP5，输出一份运营报表。

处理过程：

1. Supervisor 判断为学情分析任务；
2. 提取时间范围、课程/班级范围、指标和 Markdown 输出格式；
3. 权限服务确认运营人员可访问的校区和班级；
4. 学情分析智能体选择 class_attendance_analysis 任务模板；
5. 固定模板直接使用参数化 SQL/Python，复杂任务再通过 A2A 调用独立分析服务；
6. DSH 在脱敏数据快照上执行受控计算，并返回指标和 Artifact；
7. 学情分析智能体检查数据边界、统计口径和敏感字段；
8. Supervisor 汇总结果，通过 SSE 返回报表；
9. 失败时有限重试，仍失败则转人工并保留 task_id。

## 九、分阶段实现

### 阶段 1：逻辑三智能体，全部进程内

- 保留 Supervisor、FAQ、学情分析三个角色；
- 不急于拆成三个独立进程；
- 用 LangGraph 条件边表达路由；
- 先保证 FAQ 和个人学情查询稳定。

### 阶段 2：学情分析确定性能力

- 增加个人课时摘要、班级完课率和缺勤 TOP5；
- 所有数字由 SQL/Python 计算；
- 做权限、口径和边界值回归测试；
- 报表只是 output_format，不增加报表智能体。

### 阶段 3：学情分析服务化

- 将学情分析智能体抽成独立服务；
- 使用内部任务契约隔离 Supervisor 与分析实现；
- 先用本地适配器验证服务边界。

### 阶段 4：A2A 远程协作

- 为学情分析服务增加 A2A Agent Card 和 Task 适配；
- 加入超时、重试、取消、状态同步和 Artifact；
- 只对复杂、长耗时和需要隔离的任务启用。

### 阶段 5：DSH 受控执行验证

- 验证实际 DSH 版本是否支持沙箱、超时、资源限制、工具白名单和产物管理；
- 使用脱敏快照，不连接生产库；
- 如果实际 DSH 只提供模型封装，则不强行引入，保留确定性分析服务。

## 十、答辩可直接使用的结论

> 我们最终采用逻辑上的三智能体架构：Supervisor 主控智能体、FAQ 知识问答智能体和学情分析智能体。报表没有单独拆成智能体，因为报表只是学情分析结果的一种输出形式。Supervisor 负责理解请求和编排流程，FAQ 智能体负责非结构化课程规则，学情分析智能体负责结构化课时和出勤分析。简单查询走进程内调用，复杂或长耗时的学情分析再通过 A2A 调用独立服务，必要时由该服务内部使用 DSH 沙箱执行。这样既体现多智能体协作，又避免职责重复和过度设计。

## 十一、面试追问

### Q1：为什么不直接采用两个智能体？

**答：** 两个业务智能体在 MVP 阶段可行，但 Supervisor 承担意图识别、任务委派、重试和人工兜底，这些职责与 FAQ 和学情业务逻辑不同。实现上可以先在同一个 LangGraph 进程内运行，逻辑角色独立不等于必须立刻拆成独立服务。

### Q2：三个智能体是不是过度设计？

**答：** 如果三个智能体都独立部署，确实可能过度设计。因此本项目采用逻辑三智能体、分阶段部署：三个角色先在一个 LangGraph 进程内协作，只有学情分析出现长耗时、代码执行和独立扩容需求时，才通过 A2A 服务化。

### Q3：为什么不把报表独立成智能体？

**答：** 报表是输出格式，完课率和缺勤 TOP5 的数据来源、权限和统计口径仍属于学情分析域。独立拆出报表智能体会重复权限和数据逻辑，也会让职责边界模糊。

### Q4：A2A 的价值是什么？

**答：** A2A 的价值不是自动提高答案准确率，而是为学情分析智能体提供跨服务任务协作能力。当分析任务需要异步处理、独立资源、沙箱执行和 Artifact 审计时，A2A 可以表达任务状态并隔离故障；对低延迟 FAQ 则没有必要使用。

### Q5：DSH 的价值是什么？

**答：** DSH 的价值取决于它是否提供受控执行能力，包括沙箱、工具白名单、资源限制、超时取消和产物记录。如果它只是 DeepSeek API 的简单封装，项目没有必要为了名称引入；如果它能安全承载脱敏数据分析，就可以作为学情分析智能体内部的可替换执行器。

- **时间：** 2026-09-01
