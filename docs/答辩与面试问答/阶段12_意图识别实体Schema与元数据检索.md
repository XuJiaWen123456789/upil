# 阶段 12：意图识别、实体 Schema 与元数据检索问答

## Q1：为什么不只在提示词中完成意图识别和指代消解？

提示词适合规定角色、回答风格和证据边界，但不能可靠承担持久会话状态、
实体覆盖和业务路由。uPil 将意图和实体定义为 Pydantic 结构，将当前实体
保存在 LangGraph State，并用确定性代码执行“本轮明确实体覆盖历史实体”，
从而降低模型在多轮课程切换中沿用旧属性的风险。

## Q2：为什么采用通用 EntityReference，而不是给每类文档建一个大 Schema？

文档数量不等于实体类型数量。对话状态只需保存实体类型、标准名称、原始
表达、是否显式、是否纠正和置信度。课程年龄、教师履历、校区地址等事实
仍由知识库或业务工具提供。这样既能支持课程、教师和校区，又不会产生大量
空字段，也避免把不同实体的属性错误混在一个大模型输出中。

## Q3：RAGFlow 文档元数据在系统中有什么作用？

元数据用于限定检索范围，例如课程详情优先检索 `course_catalog`，教师问题
优先检索 `teacher_profile`。它能减少跨业务文档串扰，并支持可见范围、版本和
文档状态治理。元数据不能替代实体识别和指代消解，而是 LangGraph 结构化理解
与 RAGFlow 检索之间的桥梁。

## Q4：为什么元数据过滤必须设计降级重试？

意图分类或文档标注都可能出错。如果错误使用强过滤，正确资料会被完全排除。
因此正式方案只在高置信度时过滤；过滤无结果或证据不足时取消业务类型过滤
重试，同时继续保留服务端强制的权限过滤。这样在提高精确率的同时控制漏召回。

## Q5：课程名称为什么要标准化？

家长可能使用“编程项目班”“编程项目实践”等简称，而知识库使用“编程项目
实践班”。标准化能把多个自然语言表达映射到同一实体，使会话状态、检索查询、
测试断言和日志都使用统一名称。当前使用受控别名表，未来可由课程目录数据库
或教务 API 提供标准实体列表。

## Q6：怎样处理“不是舞蹈，是编程项目实践班”？

系统首先识别本轮显式出现的“编程项目实践班”和纠正标记“不是/是”，然后用
新实体覆盖历史的“中国舞进阶班”。检索改写会去掉否定部分，只提交“编程项目
实践班”及后续属性问题，避免旧课程词语继续影响全文和向量检索。

## Q7：怎样处理“这个课程”“适合几岁”这类追问？

如果本轮没有新实体，但存在明确课程指代，系统把指代替换为当前课程标准名；
如果省略指代词但询问年龄、时长或基础等课程属性，则在查询前补充当前课程名。
“谢谢”“还有呢”等没有明确属性的短句不会强制继承课程，避免过度指代。

## Q8：当前能力为什么还不能称为完整生产级指代消解？

当前第一轮只完成确定性的课程基线，还没有接入结构化 LLM、持久会话存储、
教师和校区白名单、歧义澄清、多实体比较与动态 RAGFlow 元数据过滤。其价值是
先通过单元测试固定最重要的实体更新规则，再逐步接入模型和工作流，降低回归风险。

## Q9：本阶段如何验证而不是只靠人工体验？

测试覆盖课程别名、具体课程优先、显式纠正、课程指代、省略指代词、普通寒暄、
三轮实体切换、置信度校验和通用教师实体。新增测试 9 项全部通过，全量测试
42 项通过。RAGFlow 元数据也完成无过滤、正确过滤和错误过滤的 A/B 验证。

## Q10：为什么真实模型测试之外还需要 Fake Model 单元测试？

真实模型能够验证中文语义、Prompt 遵循和供应商接口，但结果会受到网络、限流、
模型版本、费用和随机性的影响。Fake Model 用于稳定验证非法 JSON、未知路由、
超时、白名单外课程和 Prompt 注入等故障分支。两者分别验证“模型实际效果”和
“系统安全边界”，不能互相替代。

## Q11：为什么高风险意图要由确定性守卫优先，而不是全部交给 LLM？

课时、出勤、实时名额、排课和退费金额涉及动态数据、隐私或交易。如果模型把
这些问题误判为普通 FAQ，可能直接使用静态知识回答并产生越权或虚假承诺。
因此 uPil 在调用模型前先识别高风险关键词，强制设置 needs_live_data=true，
后续只能进入受权限保护的业务工具或人工流程。LLM 负责复杂语义补充，而不是
绕过业务边界。

## Q12：Pydantic 校验和 Prompt 中要求 JSON 有什么区别？

Prompt 只是对模型的软约束，模型仍可能输出代码块、非法枚举、额外字段或错误
类型。Pydantic 是运行时硬校验：意图必须属于枚举，置信度必须在 0 到 1，未知
字段被禁止。通过结构校验后还要执行课程白名单和实时数据规则，形成“语法结构、
实体真实性、业务安全”三层校验。

## Q13：真实 DeepSeek 测试发现了什么问题，如何修复？

首次 8 个用例通过 7 个。问题“6 岁孩子适合学中国舞还是美术”被正确识别为
课程推荐，但模型在单实体字段中只保留了“美术”，可能污染后续活动实体。
系统随后增加多候选检测：推荐问题含两个及以上课程候选时，不从中任选一个写入
当前实体，也不因为比较本身强制澄清。修复后同一套真实测试达到 8/8。未来若需
分别检索和比较多个对象，再新增独立的 candidate_entities，而不是滥用单实体字段。

## Q14：怎样证明测试确实调用了模型，而不是回退规则恰好答对？

适配器返回额外的来源诊断：model 表示结构化模型输出通过全部校验，
deterministic_guard 表示高风险规则在模型前拦截，deterministic_fallback 表示
模型未配置、超时、限流或输出非法后降级。真实评估要求普通语义用例必须来自
model，从而避免把回退结果误算成模型准确率。

## Q15：怎样处理 429、超时和外部模型不可用？

当前模型请求超时为 20 秒，SDK 最大重试次数为 1，避免限流时形成重试风暴。
异常不会直接返回给用户，而是转换为确定性回退结果并记录安全的失败原因类型。
正式接入在线链路后还应增加请求耗时、429 次数、模型成功率、回退率和意图混淆
矩阵等监控指标，并根据业务 SLA 决定熔断策略。

## Q16：为什么当前不能声称结构化意图识别已经在线生效？

本阶段完成的是独立适配器、离线契约测试和 DeepSeek 真实模型评估。现有
/api/v1/chat/stream 仍使用旧关键词路由，LangGraph State 也尚未持久化
active_entity 和 rewritten_query。只有下一阶段完成会话 ID、状态管理、路由
映射和 SSE 回归后，才能说明结构化识别已经进入在线请求链路。
## Q17：为什么开发期会话状态不能直接作为生产方案？

答：当前 `InMemoryConversationStore` 的价值是快速验证实体覆盖、指代消解、
TTL 和会话隔离，但它依赖单个 Python 进程。服务重启会丢状态，多 Worker
之间也无法共享，无法支持生产扩缩容。生产应把相同状态契约迁移到 Redis，
或使用 LangGraph PostgreSQL Checkpointer，并增加用户身份绑定、分布式并发
控制、过期清理和审计策略。

## Q18：为什么结构化意图识别要通过依赖注入接入 SSE？

答：如果在模块导入时直接构造真实模型并让测试共用，开发机 `.env` 会让
普通单元测试访问网络，造成慢、贵、不稳定和 429。依赖注入使生产链路使用
DeepSeek，而测试注入 Fake Model 或 `None`，既能验证业务契约，又能单独运行
显式真实模型冒烟测试。

## Q19：为什么实时名额问题不进入 RAGFlow？

答：RAGFlow 中的课程手册是静态知识，只能说明班型和规则，不能证明此刻
是否有空位。把实时问题交给静态 RAG 会产生“有依据但已过期”的幻觉。当前
系统通过确定性守卫标记 `needs_live_data=true`；有学情工具的请求进入数据库，
尚未接入名额工具的请求安全转人工，未来再替换为教务查询工具。

## Q20：三轮课程切换为什么要改写检索问题？

答：用户可能先问中国舞，再纠正为编程项目实践班，最后只说“这个课程”。
直接检索最后一句缺少实体，RAG 容易召回错误课程。系统将最后一句改写成
“编程项目实践班适合多大孩子？需要什么基础？”，使每轮检索问题语义完整，
同时保存显式纠正后的最新实体，避免旧课程污染上下文。

## Q21：为什么知识库文档要分批导入，而不是一次性全部上传？

答：分批导入可以把解析失败、Chunk 串行、图片噪声和检索误召回定位到单份文档。
每份资料只有在完成“上传、元数据、解析、Chunk 抽查、固定问题检索”后才标记
为 `validated`。如果一次性导入全部资料，出现错误时难以判断是源文档、Embedding、
切块参数还是跨文档竞争导致，也不利于建立可回滚的知识版本。

## Q22：怎样证明课程价值文档不是只上传成功，而是完成了可用性验收？

答：系统不仅检查解析状态，还逐一查看 8 个 Chunk，并用舞蹈、美术、编程和音乐
四个固定问题做检索。记录 Top 1/Top 2 文件、混合相似度和证据正文，同时检查
“不承诺竞赛结果”“不保证个体学习效果”等边界是否仍保留。验收完成后才把
清单状态从 `pending` 改为 `validated`，因此“已上传”和“已验证”有明确区别。

## Q23：RAGFlow 解析失败时，怎样判断是文档问题还是 Embedding 服务问题？

答：本次错误明确为 `Fail to bind embedding model` 和无法连接 Ollama，而同一文档
内容没有解析语法错误。排查时分别验证 Windows 到 Ollama、RAGFlow 容器到 Ollama
的 `/api/version` 和 `/api/tags`。容器链路恢复后，在不修改文档和切块参数的情况
下重新解析成功，证明根因是 Embedding 服务连通性，不是文档内容。

## Q24：为什么 Docker 容器访问宿主机 Ollama 使用 host.docker.internal？

答：容器中的 `127.0.0.1` 指向容器自身，不是 Windows 宿主机。Docker Desktop 为
容器提供 `host.docker.internal` 作为宿主机稳定入口，因此 RAGFlow 应通过
`http://host.docker.internal:11434` 访问 Ollama。直接使用某个桥接网关 IP 容易随
环境变化，也可能因监听地址和防火墙被拒绝。

## Q25：固定问题的 Top 1 不是最细粒度详情，就说明 RAG 失败了吗？

答：不一定。例如美术和编程问题的 Top 1 是完整能力培养地图，而专属课程价值
详情位于 Top 2，两者都能支持正确结论。验收应同时看 Recall@K、证据充分性和
最终答案，而不能只看 Top 1。但如果 Top K 没有专属证据，或生成层长期选择过于
宽泛的片段，则需要做查询改写、元数据路由或重排，而不是盲目调低阈值。

## Q26：为什么教师资料必须按教师独立分块？

答：教师履历、教龄、授课风格和主教方向都属于强实体属性。如果两个教师落入
同一 Chunk，模型可能把甲教师的履历归给乙教师，形成事实串行。uPil 让每位教师
保持独立标题和独立 Chunk，并用“教师方向 + 属性”固定问题验证 Top 1，从数据结构
和检索测试两层降低错误归属风险。

## Q27：怎样防止不同教师的履历和授课风格串行？

答：第一层在源文档按教师设置明确标题和完整自包含段落；第二层在检索前识别
课程方向或教师实体并改写查询；第三层生成答案时只使用命中教师的最小必要证据；
第四层用林老师、周老师、陈老师的交叉测试检查答案是否混入其他教师属性。未来
教师数量增加后，还可以按 `teacher_id` 增加 Chunk 或实体级元数据。

## Q28：为什么教师联系方式不能进入公开知识库？

答：公开 RAG 会被大量用户检索，教师手机号、证书编号等信息一旦索引，就可能在
不相关问题、提示注入或日志中被召回。正确做法是源头不入库，而不是只依赖 Prompt
要求模型保密；对外只提供经过审核的公开资料，联系需求走教务或授权业务流程。

## Q29：为什么示例课表不能用于回答实时排课？

答：示例课表只用于展示数据结构和图文检索能力，不带当前时间、班级变更和学员
身份。即使它与用户问题高度相似，也不能证明“今天在哪间教室”。系统应把“今天、
当前、还有名额”等词识别为动态数据意图，强制调用教务工具；工具未接入或失败时
转人工，不能把静态示例当作事实。

## Q30：Markdown 中包含图片引用是否等于完成了多模态 RAG？

答：不等于。当前 RAGFlow Chunk 只保存 `![替代文本](相对路径)`，图片原件没有
通过 MinIO 提供稳定对象地址，也没有建立 OCR、图像描述、权限和图片引用返回链路。
因此当前只能称为“图文语料结构预留”。完成多模态 RAG 还需上传授权图片、生成并
审核语义描述、建立对象存储映射，并验证检索结果能安全返回对应图片。

## Q31：为什么“校区有哪些教学空间”没有 Top 1 命中时不立刻全局调权重？

答：该问题中的“教学”是通用高频词，在全文权重 0.70 时会让教师资料获得较高
关键词分。把向量权重临时提高到 0.60 能使校区 Chunk 升为 Top 1，但全局改参可能
损害课程名称、规则编号等精确匹配。uPil 先用意图识别把问题改写为“校区环境中
设置了哪些功能区”，在原参数下即可 Top 1 命中；之后再用完整评测集决定全局参数。

## Q32：为什么“首次到校区前台需要登记哪些信息”要做查询改写？

答：原问题中的“首次到校区”和“前台登记”同时出现在校区服务资料与到访安全提示中，
如果直接检索，可能只召回“需要在前台登记”这一条不完整证据。系统将问题改写为
“到访与咨询流程中，首次到校区前台需要登记哪些信息？”，补充了“流程”和“哪些信息”
两个检索意图。在无元数据过滤的测试中，改写后的问题 Top 1 命中 `校区与服务信息.md`
的“到访与咨询流程”Chunk，混合相似度 51.05，并完整召回学员年龄、意向课程、
可上课时间段和既往学习经历。因此，查询改写不是替代 RAG，而是让检索请求更接近
用户真实意图，降低同义语料竞争和证据不完整风险。

## Q33：为什么元数据过滤生效后，目标 Chunk 仍可能不是 Top 1？

答：元数据过滤解决的是“到哪些文档中检索”，不是“同一文档中的 Chunk 如何排序”。
本次设置 `document_type=campus_service` 后，`教师与校区环境.md` 已被完全排除，证明过滤
有效；但同一份 `校区与服务信息.md` 中的“服务边界”因关键词分 23.91 高于目标 Chunk
的 20.03，在全文权重 0.70 的基线下以 40.41 的混合分排到第一。目标“到访与咨询
流程”虽然向量分更高（82.57），最终仍以 38.79 排在第二。因此生产链路需要组合
查询改写、元数据过滤和 Top K 证据选择；不能把文档级过滤误认为块级精排。

## Q34：查询改写和元数据过滤为什么要组合使用？

答：两者解决的是不同层次的问题。元数据过滤负责限定“在哪类文档中检索”，本次
`document_type=campus_service` 已成功排除 `教师与校区环境.md`；查询改写负责补齐
用户意图和业务实体，解决同一文档内部 Chunk 的排序竞争。测试 2C 同时使用两种策略后，
“到访与咨询流程”从测试 2B 的 Top 2 回到 Top 1，混合相似度为 51.05，并完整召回
四个登记字段。由此可见，元数据过滤是范围控制，查询改写是语义精确化，二者组合能
同时降低跨文档误召回和同文档证据不完整的风险。

## Q36：错误的元数据过滤测试为什么没有返回空结果，也仍然可以判定过滤通过？

答：元数据过滤的目标是限制检索范围，不是保证任何问题都返回空结果。本次设置
`document_type=course_value`，查询“校区有哪些设施？”，系统返回了同属课程价值
类型的能力培养地图，混合相似度 22.20；但没有召回 `校区与服务信息.md`，也没有
出现前台、教室、休息区或功能区等校区证据。因此，过滤范围控制是通过的。
在正式生成链路中，还要增加“证据是否真正支持问题”的判断：如果候选内容只是在
语义上相近而不能回答问题，应提示当前检索范围未覆盖，或由路由层重新选择
`campus_service` 后重试，不能让模型依据能力培养地图编造校区设施。

## Q37：为什么本项目暂时不打开 RAGFlow 的自动元数据？

答：自动元数据适合从大量非结构化资料中辅助提取主题、实体或标签，但本项目的
`document_type`、`business_scope`、`entity_type`、`data_scope` 和 `version` 要参与
检索范围控制，必须是稳定、可枚举、可审计的字段。若完全交给模型自动生成，可能出现
“编程”和“少儿编程”、“校区”和“校区服务”等同义值，导致元数据过滤不稳定。
因此当前先人工设置受控元数据，保证演示和测试可复现；未来面对大量外部文档时，
可以在测试副本中启用自动元数据，把它作为候选标签，经规范化和人工审核后再进入
正式过滤字段。自动元数据也不能修复 Chunk 边界，更不能替代查询改写或实时业务工具。

## Q35：为什么家长看课问题的 Top 1 Chunk 还包含“第一次到校区怎么走”？

答：这属于 FAQ 文档的相邻问答合并，而不是检索结果完全错误。当前 Chunk 同时包含
“第一次到校区怎么走”和“家长可以进入教室看课吗”两个相邻问题，但目标问题的核心
证据仍被完整召回：日常课程通常不安排家长进入教室，家长可以在休息区等候，机构
还会通过开放日、作品展示或阶段反馈介绍学习情况。验收时需要区分“目标证据是否存在”
和“Chunk 是否完全没有其他内容”。生成层还要执行最小证据原则，只抽取与家长看课
有关的句子，不要把同一 Chunk 中的路线、停车或发票信息扩展到答案。

## Q38：为什么“编程课需要家长提前购买电脑吗”命中课程详情，而不是装备要求文档？

答：两份文档都包含编程设备信息，但课程详情中的“设备说明”与问题表达更直接，
因此在无过滤检索下被排到 Top 1。这说明跨文档存在事实重复时，答案可能正确，
但来源未必是预设的目标文档。生产系统应根据问题意图选择 `equipment_requirements`
过滤，或在生成层优先选择字段更完整、来源更匹配的证据。当前结果不能简单判定
为 RAG 失败，但需要补充一次装备文档的来源隔离测试，确保新增文档不是“上传后
无法独立使用”。

## Q39：为什么聊天回答事实基本正确，仍然不能直接判定通过？

答：聊天验收不仅检查事实是否正确，还要检查是否泄露内部检索信息、是否超出证据范围、
是否只回答当前问题。比如“编程课需要电脑吗”的核心事实正确，但输出了“图 1”“图 2”
和来源文件名，用户不应看到这些内部标记；“家长可以预约进入课堂观摩”如果资料只写了
开放日用于介绍学习情况，也不能自行扩展为可以预约进课堂。因此公开客服验收要同时检查
事实准确性、证据边界、隐私安全和对外表达规范，不能只看回答是否大致正确。
