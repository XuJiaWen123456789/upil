# 阶段 1：项目骨架、Python 环境与 SSE 验证

## Q1【高频】为什么坚持 Python 3.11 而不是直接用机器上已有的 3.14？

**答：** 当时机器只有 3.14，我先拿来做了临时冒烟验证，但正式基线仍然锁 3.11，原因：

1. LangChain/LangGraph/psycopg 等核心依赖在 3.11 的兼容性验证最充分，3.14 太新；
2. 后续 Docker 镜像、服务器部署统一用 3.11，减少环境漂移；
3. 用 `.python-version` 文件锁死版本，任何协作者进项目都自动用对版本。

这本身就是个面试点：**临时验证环境和正式基线环境要分开，验证结果不能交叉替代**——3.14 下测试通过不等于 3.11 下没问题。

## Q2【高频】SSE 接口的设计细节？为什么事件分 status/token/complete？

**答：** 接口是 `POST /api/v1/chat/stream`，事件流设计：

```
event: status   → 阶段通知（accepted / routed），前端可展示"正在路由"
event: token    → 增量内容，前端逐字渲染
event: complete → 结束标记，携带最终路由信息
event: error    → 异常，前端展示兜底话术
```

只发 token 也能用，但用户体验差——用户不知道系统是在打字还是在思考。status 事件让前端能区分"已接收→已路由→生成中"的阶段。这是流式体验设计的基本功。

## Q3 踩坑：中文 SSE 在测试客户端乱码，怎么定位和解决的？

**答：** 现象：接口通过 curl 请求中文正常，但 pytest 里用 TestClient 断言中文内容失败。

**定位过程：** 打印 `response.text` 发现中文全是乱码 → 打印 `response.headers` 确认 content-type 是 `text/event-stream; charset=utf-8` → 再打印**原始字节** `response.content[:100].hex()`，确认字节是合法 UTF-8（如 `\xe4\xb8\xba` 就是"为"）。

**结论：** 服务端输出没问题，问题在测试工具对流式响应 `response.text` 的解码行为。

**解决：** 测试改为 `response.content.decode("utf-8")` 后再解析 SSE 事件，断言通过。

**面试价值：** 这题展示的是编码问题的标准排查链路——**从文本层下探到字节层，用 hex 眼见为实**，而不是瞎改编码参数。

## Q4 为什么 SSE 解析要自己写，而不是用现成库？

**答：** SSE 格式极简（`event: xxx\ndata: yyy\n\n`），自己写的解析器不到 10 行，带来的收益是测试不依赖第三方行为。第 1 阶段的目标是验证链路，自己解析能完全掌控中间格式。

## Q5 测试策略是什么？为什么第 1 阶段就写测试？

**答：** 4 个测试覆盖：健康检查、FAQ 路由、学情路由+内容、家长隐私提示。

第 1 阶段就写测试的原因：**骨架阶段的行为是最稳定的，此时建立的测试是后续所有重构的安全网**。第 3 阶段接真模型、第 5 阶段接 DSH 时，这 4 个测试保证基础路由不被破坏。

隐私测试单独成条：家长不带学员编号问课时，必须返回引导话术而不是数据——这是业务红线，必须有回归测试。

## Q6 为什么对话入口是 POST 而不是 GET？

**答：** 对话请求带 message、actor_role、learner_id 等结构化参数和潜在长文本，POST + JSON body 是正确语义。GET 挂 query 参数有 URL 长度限制和敏感信息进日志的问题。（浏览器原生 EventSource 只支持 GET，所以前端用 fetch + ReadableStream 读取，这也是选 SSE 时要提前想到的细节。）
