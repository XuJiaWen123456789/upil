# 阶段 12-J：结构化工具调用与可观测性答辩问答

## Q1：为什么要同时设计 request_id 和 tool_call_id？

**答：** request_id 表示一次入口请求，可串联路由、智能体和工具层；tool_call_id 表示该请求中的某一次具体工具调用。同一个 request_id 下未来可能发生多次调用或重试，因此二者不能合并。这样能准确定位“哪次请求中的哪次工具调用”发生了超时或失败。

## Q2：统一错误码比中文错误信息好在哪里？

**答：** 中文文案用于面向用户解释，可能随产品文案调整；稳定错误码用于程序判断、告警和统计。项目将参数错误、访问拒绝、尚未接入、超时、不可用和执行失败分开，使上层工作流能选择重试、转人工或直接拒绝，而不需要解析中文字符串。

## Q3：工具审计日志记录了什么？为什么不记录完整请求？

**答：** 只记录追踪 ID、工具名、路由、状态、错误码、耗时、角色和结果。客服请求可能包含学员、订单和联系方式，完整问题、API Key、密码、SQL、课程参数及第三方原始响应都不进入普通审计事件，从而遵循最小必要原则并降低日志泄露风险。

## Q4：为什么不能直接开放一个让前端传 tool_name 的万能接口？

**答：** 这会扩大攻击面，用户可能绕过业务路由尝试调用不属于当前场景的工具。项目采用“业务路由到工具白名单”的显式映射，后续即使增加 HTTP 演示接口，也只提供固定用途、固定参数模型的受控接口，而不是执行任意工具名。

## Q5：当前身份核验达到生产标准了吗？

**答：** 没有。当前 actor_role 和演示用户 ID 用于本地联调，has_verified_identity 是受控的开发标志。生产环境必须从 JWT、OAuth2、SSO 或 API 网关认证上下文获得用户身份和角色，不能相信客户端提交的 actor_role、actor_user_id 或身份核验布尔值。

## Q6：这个阶段如何支持后续 A2A 和 DSH？

**答：** A2A 是跨进程、跨智能体任务协作，故障定位比本地函数调用更复杂。当前先稳定 request_id 和 tool_call_id；未来可将 A2A 的 task_id、correlation_id、parent_task_id、artifact_id 与现有追踪字段建立映射，从主智能体一路追踪到 DSH 子节点及返回产物。

## Q7：当前是否已经接入真实教务、订单和工单系统？

**答：** 没有。学情查询来自本地演示数据库；其他动态系统通过协议和 Fake Adapter 验证超时、不可用和幂等边界。未接入的工具会返回 TOOL_NOT_IMPLEMENTED 或安全降级，绝不伪造实时名额、订单状态和退款金额。

## Q8：阶段 12-J 的自动化验证覆盖哪些内容？

**答：** 覆盖追踪 ID 存在及唯一性、执行耗时非负、路由与身份拒绝、未实现工具错误码、适配器超时错误码、审计事件最小字段、敏感参数不进入审计，以及 LangGraph 学情链路回归。当前全量结果为 90 passed、1 skipped。
