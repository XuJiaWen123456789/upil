# 阶段 12-K：内部工具接口与请求追踪答辩问答

## Q1：为什么要增加 X-Request-ID？

**答：** 一次客服请求可能经过 HTTP 入口、意图识别、LangGraph 节点和业务工具。`X-Request-ID`把这些环节串成一条可定位链路，发生超时或错误时可以快速根据同一个 ID 检索服务日志。它只用于观测，不代表用户身份，也不承担认证和授权职责。

## Q2：客户端传入的 X-Request-ID 可以直接信任吗？

**答：** 不能完全信任。项目只接受由字母、数字、下划线和短横线组成、长度受限的值；缺失或包含空格、换行等非法字符时由服务端重新生成，降低日志注入风险。即使格式合法，它也只能作为链路关联线索，不能作为权限判断依据。

## Q3：为什么不开放 POST /api/v1/tools/execute 让前端传 tool_name？

**答：** 这种万能接口会让调用方绕过业务路由和工具白名单，扩大越权调用、敏感查询和命令注入风险。项目提供的是固定用途接口，路径、请求模型、工具名称和业务场景都由服务端写死，调用方不能传入任意工具名、SQL 或命令。

## Q4：固定班级名额接口返回的 3 个名额是真的吗？

**答：** 不是生产实时数据，而是本地 Fake Adapter 的确定性演示结果，仅用于验证 HTTP 链路、工具契约和前端展示。接口响应明确标注“仅用于本地测试，不代表实时名额”。真正上线时需要替换为经过认证、限时和审计的教务系统适配器。

## Q5：为什么演示接口只允许 development、test、local 环境？

**答：** 它的返回值是演示数据，且没有生产级的身份认证和真实业务授权，因此不应暴露到生产环境。代码在其他环境直接返回 404，避免外部调用方发现并使用本地演示能力。生产接入应使用独立内部网络、认证和真实适配器。

## Q6：HTTP 请求 ID 如何传到 LangGraph 和业务工具？

**答：** FastAPI 中间件先生成或校验追踪 ID并写入 `request.state`。SSE 入口读取它并写入 LangGraph 状态；学情节点调用工具注册表时继续透传，工具结果和脱敏审计事件再记录同一个 request_id。这样不需要把内部 ID 拼进家长可见的回答正文。

## Q7：为什么 SSE 不把 request_id 作为回答内容返回？

**答：** request_id 是内部排障字段，不是业务答案。将它写入回答会增加用户认知负担，也可能被误认为业务编号。项目通过 HTTP 响应头返回它；前端或客服在用户反馈问题时可以读取并提交该 ID，后台据此定位日志。

## Q8：未来接入 A2A 或 DSH 时如何扩展？

**答：** 保留当前 request_id 作为上游关联 ID，并在 A2A Task 中增加 task_id、parent_task_id 和 correlation_id；DSH 产生的脚本、报表等结果用 artifact_id 标识。跨服务日志统一记录关联字段，但仍不记录 API Key、原始隐私数据或完整用户问题。

## Q9：本阶段测试覆盖什么？

**答：** 覆盖服务端自动生成请求 ID、合法 ID 透传、非法 ID 替换、固定班级名额演示接口成功返回，以及通过额外 `tool_name` 字段请求时被 Pydantic 拒绝。定向 API 与工具测试结果为 36 passed，全量回归为 95 passed、1 skipped；真实本地 HTTP 联调也验证了健康检查、追踪 ID 透传和演示接口返回。
