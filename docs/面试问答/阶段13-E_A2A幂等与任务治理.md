# 阶段 13-E：A2A 幂等与任务治理答辩问答

## 1. 为什么要做 A2A 幂等？

网络调用存在一个典型问题：服务端可能已经完成任务，但客户端在等待响应时超时。
如果客户端重新生成任务并再次提交，学情分析可能被执行两次，带来重复计算、重复计费
或重复写入的风险。因此系统让客户端重试时复用同一个 `task_id`，服务端通过任务仓库
返回第一次结果。

## 2. 只有 task_id 相同就直接返回结果吗？

不是。系统还会对完整规范化任务计算 SHA-256 指纹。相同 `task_id` 但任务内容不同，
会返回 409 冲突，不允许第二个任务覆盖原结果。这样可以避免调用方误复用 ID，也能发现
潜在的任务关联错误。

## 3. task_id 能不能当用户身份凭证？

不能。`task_id` 只负责幂等关联，不能证明调用者有权访问学员数据。当前内部端点仍需
服务令牌，学情数据在主系统侧先经过角色和绑定关系校验，远程节点只接收脱敏且最小化
的结构化输入。

## 4. 为什么当前不用 Redis？

本阶段重点是先验证协议语义、重复提交、冲突和超时重试行为。使用进程内线程安全仓库
可以减少环境依赖，便于自动化测试和答辩演示。它明确不适合多实例生产；生产部署时应
替换为 Redis 或 PostgreSQL，并用分布式原子操作或数据库唯一约束实现相同语义。

## 5. TTL 和容量上限解决什么问题？

任务结果不是永久数据。TTL 可自动清理长时间未使用的结果，容量上限可以防止异常流量
导致进程内存持续增长。本地默认 TTL 为 1800 秒、最多保存 1000 条，实际生产值应根据
任务耗时、并发量和合规要求调整。

## 6. 指标为什么不能记录完整任务内容？

可观测性不能以泄露隐私为代价。任务正文可能包含学员相关信息，Artifact 也可能包含
学情描述。因此本阶段只提供 received、executed、deduplicated、conflicts、completed、
failed 和 stored 等计数，不保存问题正文、学员编号、Artifact 正文或服务令牌。

## 7. 本阶段是不是已经实现官方完整 A2A？

不是。当前是项目内版本化的最小 A2A 风格协议，重点验证任务边界、跨进程调用、鉴权、
幂等、结果校验和失败降级。尚未宣称兼容官方 A2A SDK，也没有接入真实 DeepSeekHarness。

## 8. 如果服务端返回 409，客户端为什么不重试？

409 表示任务 ID 与任务内容发生冲突，属于调用语义错误，不是网络暂时不可用。继续重试
只会重复产生同一冲突，因此客户端应失败并进入日志或人工排查，而不是形成重试风暴。

## 9. 阶段成果怎么概括？

可以这样回答：

> 系统以 task_id 作为幂等键，并通过任务内容指纹识别冲突请求；即使客户端因网络超时
> 重试，同一任务也不会重复执行。本阶段使用带 TTL 和容量限制的线程安全内存仓库验证
> 语义，生产环境计划替换为 Redis 或 PostgreSQL，同时通过脱敏计数提供基础可观测性。
