# 阶段 13-G 面试/答辩问答：生产化预发布与健康检查

## Q1：为什么还要区分 dev、test 和 staging？

**答：** 三种环境的稳定性目标不同。dev 追求快速修改，允许 SQLite 和离线回退；test
追求可重复，使用 Mock 和依赖注入，不能依赖开发机状态；staging 则模拟 PostgreSQL、
MinIO、RAGFlow 和独立 A2A 服务的组合。环境分层可以避免“本地能跑”掩盖部署和网络问题，
也避免测试因外部服务波动而不稳定。

## Q2：依赖健康检查和普通 health 有什么区别？

**答：** health 是存活检查，只说明 uPil API 进程能响应；health/dependencies 是
依赖检查，分别报告数据库、MinIO、RAGFlow 和 A2A 的状态。两者不能混为一谈：RAGFlow
暂时不可用时，API 进程仍可能存活，但 FAQ 应切换到安全回退或提示不可用。

## Q3：为什么依赖失败不直接让服务启动失败？

**答：** RAGFlow、模型和 A2A 是可选能力，开发和测试需要在没有这些依赖时运行。将所有
依赖设为强制启动会造成级联故障，也不利于故障定位。因此本项目把启动检查设计为可配置、
短超时、非阻断；staging 的发布编排器可以根据 degraded 状态决定是否阻断发布。

## Q4：健康接口会不会泄露敏感信息？

**答：** 不会。响应只返回服务名、环境名和有限状态值，不返回连接地址、异常正文、密码、
Token 或 API Key。探针异常在接口层折叠为 error，详细排查应通过受控日志和运维权限完成。

## Q5：为什么 MinIO 默认不是 ok？

**答：** MinIO 是媒体能力的可选依赖。开发环境可能只验证客服问答，不需要图片上传，
所以默认标记为 disabled 而不是误报故障。staging 若要验证媒体链路，显式开启
MINIO_ENABLED=true，探针只读列举桶，不会因为健康检查产生数据副作用。

## Q6：当前能否说系统已经生产上线？

**答：** 不能。准确说法是“完成生产化架构原型和本地 staging 验证”。项目使用虚构演示
数据，尚未接入真实教育机构的教务、订单、工单和生产 DSH 执行环境。生产上线还需要身份
认证、密钥管理、持久化任务状态、监控告警、TLS 和正式数据合规流程。
