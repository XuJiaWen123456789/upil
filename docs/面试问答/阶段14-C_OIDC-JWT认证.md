# 阶段 14-C：OIDC/JWT 认证面试问答

## Q1：为什么 uPil 不自己保存密码和签发 JWT？

因为密码策略、MFA、账号恢复和登录风控属于身份提供方职责。uPil 作为 Resource Server
只验证面向自身 audience 的 Access Token，可以复用 Keycloak、Auth0 或企业 SSO，减少
认证攻击面，并把工程精力放在教育业务授权上。

## Q2：JWT 验签成功是否等于可以访问所有业务数据？

不等于。验签只证明 Token 来自受信任 issuer 且未被篡改。uPil 还要将外部身份映射到
本地账号，再校验账号状态、家长学员绑定，或教师授课关系、有效报名关系与教师校区范围。认证回答“是谁”，
授权回答“能访问什么”。

## Q3：为什么不能直接把 `sub` 当作本地用户 ID？

`sub` 是 IdP 的主体标识，不属于 uPil 业务编号空间。更换 IdP、合并租户或导入历史用户
时二者通常不同。显式映射可以解耦外部身份和本地业务账号，也支持在不改业务外键的情况
下更换认证系统。

## Q4：为什么主键是 `issuer + subject`？

OIDC 只保证 `sub` 在一个 issuer 内唯一，不保证全球唯一。单独使用 `sub` 可能把两个 IdP
中相同字符串错误映射成同一用户，所以必须使用联合键。

## Q5：为什么不按邮箱自动映射？

邮箱可变、可能复用，且不同 IdP 的邮箱验证语义不完全一致。按邮箱静默绑定会造成账号
接管风险。邮箱适合展示和人工核对，不适合作为长期授权主键。

## Q6：为什么不信任 JWT 中的 `role=admin`？

`admin` 根本不是 uPil 支持的业务角色。IdP 角色往往描述统一身份系统权限，不等同于 uPil
业务权限；声明映射错误或租户配置漂移都可能造成越权。uPil 只从本地数据库承认 `parent`
和 `teacher`，教师校区也只读本地数据，因此 Token 中的高权限声明不能扩大权限。

## Q7：JWT、Session 和可信网关 Header 如何取舍？

- JWT 适合 API、多客户端和跨服务场景，服务可本地验签，但要处理密钥轮换与撤销延迟。
- Session 适合传统 Web，服务端易主动撤销，但需要共享会话存储和 Cookie 安全治理。
- 可信 Header 适合企业已有认证网关的内网服务，但必须清洗外部 Header、隔离后端网络并
  保护网关到服务的身份凭据。

uPil 保留 `oidc_jwt` 和 `trusted_headers`，二者统一输出 `AccessContext`。

## Q8：JWT 具体校验哪些内容？

先限制服务端允许的非对称算法，再按 `kid` 从 JWKS 唯一选择签名公钥，最后校验签名、
`iss`、`aud`、`exp`、`iat` 和主体声明。不能只做 Base64 解码，也不能只验签而忽略受众
和签发方。

## Q9：为什么拒绝 `HS256`？

OIDC JWKS 发布的是公钥。若实现允许算法由 Token Header 自由切换，错误代码可能把公钥
材料当作 HMAC Secret，形成算法混淆。uPil 固定非对称算法白名单，并在访问 JWKS 前拒绝
不允许的算法。

## Q10：JWKS 如何处理 IdP 密钥轮换？

服务按 TTL 缓存 JWKS。Token 的 `kid` 未命中时强制刷新一次，再重新选 Key。普通缓存
时间和强制刷新时间分离，所以刚完成普通拉取也能恢复轮换。刷新后仍未命中则统一返回
401，不尝试未知公钥。

## Q11：为什么未知 `kid` 需要刷新冷却？

攻击者可以构造大量不同 `kid`。如果每个请求都强制访问 IdP，会形成请求放大并拖垮
认证依赖。uPil 对未知 `kid` 的强制刷新设置 30 秒冷却，在支持真实轮换的同时限制出站
流量。

## Q12：身份库或 JWKS 故障时为什么必须 fail closed？

依赖故障意味着服务无法可信地确认身份或权限。回退到 Demo、缓存角色或相信客户端字段
都会把可用性故障变成越权漏洞，因此返回脱敏 503，让网关重试、熔断或告警。

## Q13：为什么首次登录不能根据 Token 自动创建业务用户或提升角色？

认证成功只说明用户存在于 IdP，不说明其已获准使用 uPil，也不能证明其是家长还是教师。
账号和亲子/授课关系必须通过受控流程建立。后续即使做 JIT Provisioning，也只能创建
无业务数据权限的待确认账号，不能根据客户端声明自动赋予教师权限。

## Q14：`401`、`403`、`404`、`503` 如何区分？

- `401`：身份未建立或凭据无效，包括映射缺失和账号停用。
- `403`：身份有效，但没有执行某类操作的权限。
- `404`：资源不存在或当前用户无权知道它是否存在，防止资源枚举。
- `503`：认证依赖不可用或本地权限配置不完整。

## Q15：进程内 JWKS 缓存有什么限制？

每个 API Worker 都有独立缓存，重启后会重新拉取，多实例轮换时也可能产生少量重复请求。
优点是验签不依赖共享缓存。生产应通过合理 TTL、连接超时、指标与告警控制影响；只有规模
证明必要时才引入共享缓存或 JWKS 代理。

## Q16：如何支持用户离职或权限撤销？

当前可以停用外部身份映射或本地用户，后续请求会被拒绝；教师角色和校区变化也立即以数据库
为准。JWT 在到期前仍能证明 IdP 身份，因此更严格的即时撤销需要短 Token TTL、IdP 会话
撤销、Token introspection 或风险黑名单配合。当前项目尚未实现完整即时撤销链路。

## Q17：怎么证明这不是只写了一个 JWT 解码函数？

实现覆盖配置启动门禁、Bearer 提取、算法白名单、JWKS 限量获取与轮换、标准声明验证、
外部身份映射、本地 RBAC/数据范围、失败关闭、脱敏日志、数据库迁移、运维绑定脚本以及
FastAPI 入口级回归。测试还证明伪造 `role=admin` 会被当作不受支持的外部声明，既不会
创建第三种业务角色，也不会突破家长或教师的本地数据范围。

## Q18：当前可以怎样写进简历？

可以写“实现 Resource Server 侧 OIDC/JWT 验证、JWKS 缓存与密钥轮换、外部身份映射，
并将认证上下文统一接入 FastAPI、LangGraph 与本地数据权限控制”。不能写“完成企业 SSO
生产上线”，因为真实 IdP、MFA、生命周期同步和生产发布尚未实施。
