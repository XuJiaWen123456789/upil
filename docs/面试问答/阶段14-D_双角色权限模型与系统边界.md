# 阶段 14-D：双角色权限模型与系统边界面试问答

## Q1：为什么取消管理员和校区运营端？

因为 uPil 的核心价值是家长咨询、个人学情查询和教师班级学情辅助。校区聚合经营数据会
继续引出财务、招生、排课和绩效管理，扩大数据权限与交付范围，使项目偏离 Agent 应用。
收缩后主链路更完整，安全模型和测试矩阵也更容易达到生产质量。

## Q2：取消校区运营端后，为什么还保留 `campus_id`？

它是数据归属和越权隔离字段，不是运营角色。教师除授课关系外还必须处于班级所属校区
范围，防止教师调动、数据配置错误或伪造班级编号造成跨校区读取。

## Q3：家长如何防止读取其他孩子？

访问前查询 `parent_learners` 显式绑定关系，不相信客户端提交的 learner_id、姓名或手机号。
不存在和无权限都返回 404，避免通过状态码差异枚举学员。

## Q4：教师为什么需要授课关系、有效报名和校区范围三重校验？

授课关系证明教师负责该班；有效报名证明学员当前属于该班；校区范围阻止跨校区访问。
三者分别解决不同的越权路径，任一缺失都不能推出教师有权读取学员数据。

## Q5：为什么未知角色必须默认拒绝？

权限代码如果把未知角色当成教师、内部人员或全局用户，未来新增字段或历史数据残留就可能
意外提权。白名单只接受 parent/teacher，其他值在输入、认证和授权层逐级失败关闭。

## Q6：为什么运维人员不拥有业务 API 的管理员角色？

部署、迁移、密钥和账号映射属于控制面能力，应由 CI/CD、Secret Manager、迁移工具和
受控脚本完成。把这些能力放进客服业务 API 会扩大攻击面，也会把系统推向通用后台。

## Q7：JWT 中出现 `role=admin` 怎么处理？

忽略该声明。JWT 负责证明外部身份，uPil 通过 `issuer + subject` 映射本地用户，最终角色
只从本地数据库读取。因为系统不支持 admin，所以该声明既不能创建账号也不能提升权限。

## Q8：历史管理员数据为什么停用而不是删除？

停用能立即切断登录和外部身份映射，同时保留审计、历史任务和数据外键。物理删除可能破坏
追溯链路，也不利于排查历史操作。

## Q9：为什么越权资源查询返回 404 而不是 403？

对学员和班级资源返回 403 会证明编号真实存在。统一返回 404 可以减少资源枚举风险；对于
媒体上传等动作型权限，可使用 403 表示身份有效但禁止执行该动作。

## Q10：教师既上传又审核素材是否违反职责分离？

当前版本确实存在这一生产差距。正确优化是增加 uploaded_by、reviewed_by、reviewed_at，
禁止上传者审核本人素材，或给部分教师分配 media_reviewer 权限；不应为了这一点重建校区
管理员角色和后台。

## Q11：项目收缩后还算多智能体项目吗？

算。业务角色数量与智能体数量不是一回事。系统仍由 LangGraph 路由 FAQ、个人学情、班级
学情和人工兜底，RAGFlow 负责知识检索，A2A 子节点负责脱敏学情报告增强。取消后台角色只
是收缩产品权限边界，不影响智能体编排架构。

## Q12：简历中如何描述这一阶段？

可以写：

> 将教育客服系统权限模型收敛为家长/教师双角色，基于亲子绑定、授课关系、有效报名和
> 校区范围实现资源级授权；统一 FastAPI、LangGraph、Trusted Header 与 OIDC/JWT 身份
> 边界，并通过失败关闭和 404 资源隐藏防止横向越权。
