# 阶段 15-C：多 Agent 意向识别与招生线索闭环面试问答

## Q1：报课意向 Agent 为什么是旁路，而不是直接参与回答？

主业务 Agent 的职责是回答家长当前的课程、规则或学情问题，报课意向 Agent 的职责是识别有限证据。两者并行可以避免招生判断改变正常答疑，也能让旁路超时或失败时独立降级。旁路不调用工具、不持有数据库会话、不直接写状态，最终业务动作由确定性服务控制。

## Q2：这算真正的多 Agent 吗？

算。多 Agent 的关键是职责、上下文、工具权限、失败语义和输出契约被隔离，而不是所有节点都必须在同一张 LangGraph 图中同时回答。现有 Supervisor/FAQ/服务规则/学情链负责主任务，报课意向 Agent 读取同轮脱敏副本并输出严格结构化证据，两个任务并行执行后由主系统汇合。

## Q3：为什么不把 FAQ 和服务规则全量重构成 fan-out/fan-in？

现有主链已稳定，招生识别只是低耦合旁路。全量重构会扩大回归范围，并把旁路可用性与每一次正常咨询绑定。本方案在 Supervisor 前启动异步旁路，保留原路由和流式回答，达到并行分析目的，同时把改动限制在入口编排与独立状态机。

## Q4：如何保证明确试听或报名后会自然承接并询问联系方式？

后端先用固定规则识别明确预约试听、明确报名或要求顾问联系，将其定为高意向。主回答先自然承接家长当前动作，复用已有课程、年龄和时段，但不承诺预约成功；如果线索没有已授权联系方式，状态转为 `awaiting_contact_consent`，并通过独立 `lead` SSE 事件返回固定提示：“如果您愿意由销售顾问老师继续确认试听或报名安排，请主动提供手机号或邮箱，并明确同意由销售顾问老师联系您。”该文案由后端常量生成，模型不能遗漏或改写。

## Q5：为什么“怎么试听”不是明确预约动作？

询问流程代表兴趣，但尚未表达行动承诺，因此归为中意向并进入线索池，不打断当前答疑；“我想预约试听”“请帮我这周安排试听”包含明确行动，才进入顾问队列。家长端只看到自然的下一步提示，不看到“高/中/低意向”、队列或证据码；内部强度只服务后端分流和销售顾问工作台。

## Q6：家长一发消息，系统就直接提取联系方式吗？

系统会在本地入口先检测手机号和邮箱，目的是在任何模型调用前脱敏，不等于立即保存。原值只在当前调用栈短暂存在。只有同一轮主动提供联系方式、同一轮明确授权，并且已有意向或当前轮同时明确试听/报名时，才会加密落库。

## Q7：为什么要求“同一轮明确授权”？

这能把授权与具体联系方式绑定，避免把历史模糊的“可以”误用于后续号码。只给号码、只说同意、或者没有意向时发送“同意 + 号码”，都不能绕过门禁。若号码与授权分开发送，系统要求家长在同一条消息中重新提供并明确同意。

## Q8：模型识别错了会不会直接创建高意向线索？

不会。模型只能补充低风险语义证据；明确预约、报名、顾问联系、授权和拒绝必须由本地确定性规则直接命中。强度、分流、幂等、保存联系方式和状态迁移也都在代码中完成。模型输出还经过 Pydantic 严格校验、课程白名单和超时回退。

## Q9：联系方式如何保护？

手机号和邮箱先脱敏再进入模型，数据库只保存 Fernet 密文、HMAC 指纹和脱敏展示值。普通列表与详情不返回明文、密文、家长 ID 或证据码。顾问必须先领取，再通过专用接口重新鉴权查看；响应禁止缓存，前端明文只驻留在当前页面内存，查看动作写最小审计。

## Q10：为什么销售顾问不是一个新角色？

项目已收缩为家长和教师两个业务角色。销售顾问是教师端的一项职责，用 `teacher + lead_followup` 表达比新增运营或管理员角色更符合最小权限原则，也避免产品演变成综合后台管理系统。普通授课教师不会因为角色相同自动获得线索权限。

## Q11：为什么取消运营端和转化漏斗？

本项目目标是展示多 Agent 从咨询到可执行人工跟进的闭环，而不是实现完整 CRM。运营看板、漏斗分析和跨顾问管理会引入额外角色、聚合权限与隐私范围，却不增强核心 Agent 编排。当前只保留销售顾问领取和跟进，`lead_analytics` 与历史运营账号会被清理。

## Q12：如何防止多个顾问同时处理一条线索？

领取和跟进在数据库事务中读取加锁记录。未分配线索可以领取，分配后只有所属顾问能读取和继续处理。联系方式 GET 不会隐式领取，必须先通过显式状态机动作建立归属。生产 PostgreSQL 再配合活动线索部分唯一索引控制幂等。

## Q13：旁路会不会让聊天变慢？

旁路与主链并行，等待预算从任务启动时计算，而不是主回答结束后重新计时。若主链已经消耗完旁路预算，系统立即使用确定性回退；模型超时或供应商异常也不会中断主回答。课程多轮的确定性短路还会直接处理已确认课程的年龄、基础和试听承接，避免每一轮都重新走通用检索。这样增加语义识别能力，但不让它成为咨询链路的硬依赖。

## Q14：如何验证多轮对话不是只改了文案？

验证同时覆盖：课程纠错后切换实体、“那个班”指代消解、请假插话后恢复课程、年龄/编程基础/周末上午跨轮复用、试听流程咨询与明确预约动作区分、主回答不重复询问，以及跨会话活动线索复用。专项回归 `67 passed, 3 warnings`，后端全量 `477 passed, 8 skipped, 3 warnings`；浏览器真实链路也确认最终试听回答复用了 12 岁、周末上午和本周安排。
## Q15：当前闭环完成了什么，不能宣称什么？

已完成家长对话识别、确定性分级、明确动作的自然承接、高意向主动询问、授权联系方式加密、顾问队列/线索池、领取、查看和跟进历史，并通过专项、全量和真实浏览器回放。家长端不显示内部销售强度，联系方式只有主动提供并明确授权后才保存；跨会话重复试听也会复用活动线索而不丢失授权卡。尚未接真实 CRM、电话、短信、支付、真实模型、生产 OIDC 或机构数据，因此只能宣称本地可验证的业务闭环，不能宣称生产招生系统已经上线。


## Q16：为什么“12岁，没有编程基础”不应该继续追问 Scratch？

因为这条消息已经提供了两个高置信度槽位：年龄为 12 岁，编程基础为零基础。课程推荐节点应先消费已有事实，直接说明少儿编程基础班更匹配，并保留项目实践班需要图形化基础或教师评估的边界。再次询问 Scratch 会造成重复提问和上下文不连贯。只有家长说“没做过完整项目但学过两年 Scratch”这类信息存在潜在冲突时，才应将 Scratch 识别为图形化编程基础，而不是把“没做过项目”粗暴等同于零基础。

## Q17：线索卡后为什么不能让手机号再次走 Supervisor？

手机号这一轮的首要任务不是课程问答，而是补全已经存在的线索状态。若重新走普通 Supervisor，模型或 FAQ 可能只看到脱敏后的孤立消息，无法知道它对应哪张线索卡，最终退回欢迎语。因此入口先做联系方式本地提取、格式校验和脱敏，再查询当前家长/会话下可补充联系方式的活动高意向线索；成功更新原线索，未命中才允许进入普通对话。查询范围不只包含首次 `awaiting_contact_consent`，还包含跨会话复用后仍在跟进中的活动状态，避免已授权旧线索在新会话更正联系方式时掉回 FAQ；已报名和关闭终态则不会被重新打开。

## Q18：如何避免口语化“有空位吗”被静态知识库误答？

使用确定性实时门禁，而不是只依赖几个固定关键词。规则组合识别班次、名额、空位、还能报名等可用性目标，并结合“现在/当前/目前/周末上午/工作日晚上/这个时间”等当前性或时段信息。命中后直接路由到人工确认；“什么时候上课”“一周几次”没有可用性目标，仍属于静态课程信息。这样既降低动态事实幻觉，也避免把所有时间问题都转人工。

## Q19：这次如何证明不是只修复了编程样本？

增加了四条完整 HTTP 回放，分别覆盖编程、舞蹈、美术和音乐。每条都包括课程实体与纠错、年龄或基础、服务规则插话、指代恢复、时段偏好、动态班次/名额边界、试听线索、手机号或邮箱授权，并断言最终更新的是原线索、状态为 `ready_for_followup` 且响应中没有联系方式明文。又增加跨会话复用已授权线索后更正联系方式的专项。本轮四课程回归为 `4 passed`，历史整合专项为 `140 passed`，联系方式与跨会话线索专项为 `28 passed`，后端全量为 `514 passed, 8 skipped`。

## Q20：后端不回传明文，为什么前端还要擦除家长自己发送的手机号？

因为隐私边界不只包括模型、SSE 和数据库，也包括浏览器 DOM。家长输入手机号时，原文会短暂出现在本次请求和用户消息气泡中；如果永久保留，旁观者、截图或共享设备仍可能暴露联系方式。当前实现只在请求完成后把该用户消息替换为“已提交联系方式（原文已隐藏）”，并展示后端返回的掩码。前端只负责展示期保护，不判断格式、授权或状态迁移，因此不会形成第二套业务规则；真正的脱敏、同轮授权、加密入库和线索更新仍全部由后端控制。

## Q21：销售顾问为什么不应该看到班级统计？只隐藏页面够吗？

销售顾问负责招生线索，班级统计包含授课班级、多名学员出勤和课时等教学数据，与其职责无关。只隐藏导航属于界面优化，不是授权；用户仍可能直接访问 URL 或调用接口。因此系统把普通授课教师的 `class_summary_read` 和销售顾问的 `lead_followup` 设计为互斥能力画像：前端按 capability 隐藏导航并拦截路由，后端 `can_access_class` 再次拒绝顾问访问。这样同时满足最小权限和纵深防御，也避免为了少建角色而让共用的 `teacher` 类型演变成权限合集。
