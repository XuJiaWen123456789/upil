# 项目收尾：Agent 上下文与记忆治理面试问答

## Q1：Agent 记忆是不是把对话存进向量数据库？

不是。向量库只是可能使用的一种存储组件，不能代表完整记忆系统。uPil 将记忆分为工作记忆、短期会话记忆、结构化语义记忆和程序性记忆：当前请求用不可变 ContextEnvelope，多轮指代用窗口与滚动摘要，明确确认的稳定偏好用关系表，权限和 SOP 用代码、Prompt 和工具契约固化。

## Q2：为什么不把 100 轮对话全放进上下文？

这样会造成 token 成本增长、注意力稀释和上下文腐烂。uPil 只保留最近窗口，旧轮次进入有预算的确定性摘要；课程实体和槽位保留结构化字段，动态业务事实不从摘要读取，而是重新查询工具。

## Q3：uPil 如何解决第 100 轮仍记得第 1 轮的稳定事实？

白名单内的低敏感稳定事实可以通过两种方式写入：用户明确要求“请记住”，或者出现高置信度、肯定且稳定的陈述，例如“孩子喜欢编程”“孩子小名叫果果”。查询按用户、角色、租户和学员作用域精确读取，不按 conversation_id 过滤，因此第 100 轮或一个新的会话仍可继承。普通闲聊不会无条件长期保存；当前情景记忆默认关闭，因为还没有评测过的嵌入和召回链路。

## Q4：没有嵌入模型，记忆功能会不会不可用？

不会。核心功能不依赖情景向量召回：短期多轮依赖内存/Redis 会话存储，结构化偏好依赖关系表，机构知识依赖 RAGFlow，动态学情依赖授权数据库工具。未配置嵌入模型时，情景记忆安全返回空结果，不会用未经评测的关键词检索污染回答。

## Q5：长期记忆如何防止隐私泄露？

入口先对手机号和邮箱脱敏，联系方式不进入共享上下文、摘要、长期记忆、RAGFlow 或普通日志。长期记忆只允许非敏感白名单字段，密码、Token、身份证、银行卡、课时余额、出勤、名额和报告状态会被拒绝。Agent 只拿到键和值的安全投影，看不到数据库主键、版本和来源元数据。

## Q6：用户说“记住我还剩 5 节课”会保存吗？

不会。剩余课时是动态业务事实，可能因消课发生变化，不能作为长期记忆。系统会把它拦截，后续仍通过当前权限和数据库重新计算。

## Q7：如果用户先说“喜欢编程”，系统会自动永久记住吗？

如果明确说“孩子喜欢编程”，会作为高置信度课程兴趣写入；如果只是“我想了解编程课”“孩子可能喜欢编程”或“最近暂时想学编程”，不会写入。自主判断只使用确定性白名单规则，不调用模型自由猜测，而且发现已有不同偏好时不会静默覆盖。

## Q8：记忆发生冲突时怎么办？

同一作用域、同一字段同值去重。自主判断遇到已有不同值时安全跳过；只有用户明确要求记住或修改时，才让旧 active 版本失效并创建新版本。用户删除的记录保留历史状态，允许在同一完整作用域内恢复。删除和恢复严格匹配租户、用户、角色和 learner_id，用户级 NULL 作用域使用 SQL IS NULL。

## Q9：Redis 挂了为什么不自动降级到进程内存？

生产多进程下静默降级会让不同进程看到不一致的会话，造成指代错乱和数据边界风险。当前 Redis 实现故障显式抛出受控存储异常，由上层决定错误提示或人工兜底；只有明确选择开发/测试模式时才使用进程内实现。

## Q10：短期上下文如何压缩？

最近轮次保留原始消息，旧轮次按“用户/顾问 + 脱敏文本”形成滚动摘要。摘要和总上下文都有近似 token 预算，超过预算从旧内容开始裁剪，至少保留最近两轮。摘要只用于恢复话题，不是课时、出勤和报告状态的权威来源。

## Q11：多个 Agent 如何共享上下文？

入口构造不可变 ContextEnvelope，每个 Agent 通过独立 projector 读取最小字段。Agent 不能直接写共享对象，只能返回 AgentResult；统一 reducer 只合并答案、来源和明确白名单状态，路由、权限和身份字段不可写。这样既复用同一轮解析结果，又避免旁路 Agent 越权覆盖主流程。

## Q12：为什么不用 A2A 让 Agent 共享上下文？

当前项目是单代码库、单权限域和单部署单元，同进程共享 Envelope 的成本更低、权限边界更清晰，也避免远程协议的序列化、令牌、状态映射和重试成本。A2A 适合跨团队、独立部署、异构运行时或长任务调度边界；当前场景没有这些收益，所以已移除运行链路。

## Q13：记忆写入失败会不会导致用户看不到主回答？

不会。读取结构化记忆失败返回空投影，授权查询失败返回空作用域，写入失败回滚可选记忆事务并记录固定原因码；主回答和 SSE 完成事件不依赖记忆写入成功。

## Q14：情景记忆什么时候可以打开？

需要先准备脱敏评测集、嵌入服务、召回指标、重要性/时效性策略、删除和遗忘机制，以及跨租户隔离测试。达到条件后可以实现 EpisodicMemoryStore，但不能把它直接替代 RAGFlow 或无差别保存所有聊天。

## Q15：如何证明本阶段完成？

专项测试覆盖敏感信息拦截、自主准入、显式覆盖、版本治理、主体隔离、跨会话继承、Redis 语义、上下文不可变和故障隔离。本机已执行 007 PostgreSQL 增量迁移，并完成真实表写入、新会话读取和清理冒烟验证；最终测试数字以 PROJECT_LOG 最新记录为准。真实 OIDC、机构数据以及 Redis 生产高可用仍需部署环境联调，这部分不虚报为已验收。

## Q16：为什么 uPil 要使用独立 Redis，而不复用 RAGFlow 的 Redis？

RAGFlow Redis 属于知识库基础设施，其版本、生命周期、缓存清理和淘汰策略由 RAGFlow
决定。uPil 短期会话直接影响指代消解和多轮槽位，如果复用同一实例，知识库维护可能
误伤业务会话，故障边界也无法解释。独立 Redis 只承担 uPil 会话键，凭据、数据卷、
端口和容量指标都可以独立治理。

## Q17：为什么 Redis 故障不自动回退到内存？

在多实例部署中，某个实例回退内存后只看得到自己的局部会话，下一轮请求落到其他实例
就会出现指代错乱和状态分叉。因此 Redis 模式启动时先 Ping，运行时故障显式抛出受控
存储异常；只有测试和离线工具通过明确配置选择 memory。这里优先保证一致性和故障可见性，
而不是制造表面可用但上下文错误的假降级。

## Q18：短期会话放入 Redis 后，数据边界是什么？

Redis 只保存已脱敏的最近用户/助手消息、滚动摘要、当前课程实体、孩子年龄、编程基础、
待补意图和版本号，并设置 TTL。联系方式、认证 Token、密码、课时、出勤、名额、报告状态
和知识库正文都不进入会话值。动态业务事实仍由授权数据库工具实时查询，结构化长期偏好
仍由 PostgreSQL 管理。

## Q19：单机 Redis 加 AOF 是否等于生产高可用？

不等于。AOF everysec 只改善本地容器重启后的恢复能力，无法替代哨兵/集群、跨节点副本、
备份恢复演练、容量告警和 Secret Manager。当前验收证明的是 Redis 接入与多实例共享会话
的代码边界可用，不宣称已经完成生产容灾。

## Q20：为什么不直接用模型自主决定所有长期记忆？

模型判断的字段和置信度难以稳定复现，也可能把试探、代问或临时安排升级成长期事实。当前只让确定性规则识别三个低敏感字段，并要求肯定、稳定表达；这已经实现“基本自主判断”，同时把误写风险限制在可测试范围内。未来要扩大字段，应该先增加评测集和用户管理入口，而不是直接放开自由抽取。

## Q21：为什么“请记住明天上午有空”仍然不写入？

“请记住”只表明用户希望保存，不会改变内容本身的生命周期。明天、这周、这次等属于临时安排，跨会话长期继承后很快会过期并误导推荐，所以时间字段始终执行临时周期拦截；稳定表达如“我们通常周末上午方便”才允许保存。

## Q22：新 conversation_id 为什么还能继承偏好？

conversation_id 只用于 Redis 短期会话窗口。PostgreSQL 长期记忆的查询键是租户、认证用户、角色、学员和记忆字段，来源 conversation_id 只用于最小审计，不参与读取过滤，因此更换会话编号不会丢失已经生效的稳定偏好。

## Q23：长期偏好会不会污染所有 FAQ 回答？

不会。ContextEnvelope 虽然携带安全投影，但 FAQ projector 只在“推荐课程、怎么选课、什么时候上课”等相关问题中追加课程兴趣或上课时段；孩子昵称不拼进检索问题，价格、名额、校区、请假和动态学情等查询也不会使用这些偏好覆盖权威数据。

## Q24：为什么教师消息不自动形成长期偏好？

当前三个字段描述的是家长侧孩子偏好。教师说“孩子喜欢编程”可能是在陈述课堂观察，也可能涉及多个学员；如果直接写入教师主体会形成错误档案。聊天写入门面因此只接受 parent 角色，并且带 learner_id 时仍先检查绑定权限。

## Q25：为什么“请记住孩子喜欢编程”不能交给 FAQ 或模型回答？

这是一个有副作用的记忆命令，不是普通知识问答。若先进入 FAQ，旧知识库可能返回“无法记住个人信息”；
若完全交给模型，又无法保证保存成功与回复确认的一致性。当前入口先用确定性规则识别并路由到记忆服务，
由准入、权限和事务提交决定 stored/rejected/disabled/unauthorized/failed 状态，只有 stored 才输出
“我记住了”。

## Q26：为什么“我们周末上午方便上课”之前会重复询问年龄和课程方向？

时间表达已经被识别，但没有贯穿短期会话状态和请求上下文，导致课程回答只能看到本轮时段，无法看到前文
的编程方向与年龄。修复后，class_time_preference 与课程实体、child_age、编程基础一起进入
ConversationMemory 和 Redis，并在本轮解析到新值时持久化；课程回答因此可以复用“编程 + 12岁”，
同时仍不把时段偏好当成实时班次或名额。

## Q27：显式记忆命令会不会清空当前多轮上下文？

不会。它只执行长期偏好写入，不会清除短期会话中的课程实体、年龄、编程基础和时间偏好。这样下一轮仍能
完成指代消解和槽位复用；长期 PostgreSQL 记忆与短期 Redis 会话各自承担不同生命周期。

## Q28：如何验证这次修复不是只改了回复文案？

验证同时覆盖路由、事务和真实链路：显式命令不会访问 FAQ，成功必须有数据库提交，拒绝/关闭/异常不能虚假确认；
Redis 与内存状态都能保存时间槽位；五轮回放确认最后一轮包含“周末上午、编程、12岁”且不重复追问。
本轮专项 76 passed，记忆与上下文相关回归 50 passed，后端全量 458 passed, 8 skipped。
## Q29：为什么聊天历史不能只放在 Redis？

Redis 适合保存短期高频状态，但会受 TTL、淘汰和运维清理影响，无法承担用户可管理的历史目录。uPil 用 PostgreSQL 保存会话目录、脱敏消息和受控快照，用 Redis 保存当前实体、槽位、pending、摘要和最近窗口。Redis 到期不等于历史丢失，继续旧会话时可以从数据库受控恢复。

## Q30：为什么不直接把 PostgreSQL 中的完整历史重新塞进 Prompt？

会造成 token 成本增长、注意力稀释和上下文腐烂。恢复只加载结构化白名单快照和有限最近消息，之后仍执行最近窗口、滚动摘要和 token 预算；数据库历史主要服务用户查看，而不是无限扩张模型上下文。

## Q31：会话历史如何实现多用户隔离？

服务端使用 `tenant_id + owner_user_id + owner_role + conversation_id` 做完整查询条件，所有者来自认证后的 `AccessContext`，不信任前端传入的用户 ID。列表、读取、重命名、删除和聊天续接都走同一门禁，不存在与越权统一返回 404，避免枚举他人会话。

## Q32：为什么会话校验要放在 SSE 建立之前？

`StreamingResponse` 一旦开始发送响应头，后续发现越权或数据库恢复失败就无法再返回正确的 404/503，只能在一个表面 200 的流里报错。uPil 因此先校验所有权并完成恢复，再创建 SSE，让 HTTP 状态、权限语义和客户端行为保持一致。

## Q33：Redis 过期后如何避免数据库旧快照覆盖正在使用的新状态？

恢复接口在 Redis 分布式锁内执行 only-if-empty 检查。只有当前状态确实为空时才写入数据库快照；只要 Redis 已有任一新实体、槽位、摘要、最近消息或版本，恢复就返回 false，不覆盖新状态。

## Q34：聊天消息持久化如何处理手机号和邮箱？

入口先在任何 Supervisor、旁路 Agent 和 FAQ 调用前脱敏；写入 PostgreSQL 前再执行一次手机号、邮箱、Token 和内部地址脱敏。邮箱正则使用 ASCII 边界，因为 Unicode `\w` 会把中文“或”等字符视为单词字符，导致紧邻中文的邮箱漏匹配。前端完成联系方式请求后也会擦除页面原文。

## Q35：删除聊天会话为什么不删除线索、报告和长期偏好？

聊天历史是用户界面记录，线索是经授权形成的销售业务记录，报告是正式产物，长期偏好是跨会话语义记忆，生命周期和合规依据不同。如果简单级联会造成业务数据误删。当前只删除目录、消息和 Redis 短期状态，其他记录按各自领域策略治理。

## Q36：会话标题如何生成，为什么手动标题不会被覆盖？

第一条脱敏用户消息可以生成短标题，避免所有条目都显示“新会话”；一旦用户手动重命名，`title_is_custom` 被设为 true，后续任何自动标题都不得覆盖，保证用户对目录名称的控制权。

## Q37：为什么还要测试服务规则回答的历史持久化？

SSE 分支可能正常把 chunk 发给浏览器，却忘记把 chunk 汇总进最终 `answer_parts`。这种缺陷实时聊天看起来正常，但刷新页面后 assistant 消息为空。uPil 增加了请假规则双 chunk 回归，要求数据库历史中的回答与流式拼接结果完全一致。

## Q38：为什么当前不把完整聊天历史写入向量数据库？

本阶段需要的是确定性的列表、继续、删除和 Redis 恢复，关系库按主体和顺序查询更合适。完整聊天无筛选向量化会增加隐私、删除一致性和召回污染问题，而且不能替代结构化槽位与权限校验。只有未来建立脱敏准入、情景召回评测和遗忘策略后，才考虑对少量高价值片段做向量化。

## Q39：代码已经实现长期记忆，为什么页面仍可能回答“暂时无法保存”？

能力是否可用同时取决于代码、数据库迁移和部署配置。uPil 的根目录开发 .env 与
staging 私有 .env.staging 分开加载；页面访问 18000 时使用后者。如果该环境没有
开启 MEMORY_WRITE_ENABLED，服务会按默认关闭值返回 disabled，即使表和代码均正常。
因此排查顺序应是运行时配置、迁移表、权限作用域、事务结果，而不是先改回复文案。

## Q40：为什么“请根据以前记住的偏好推荐课程”不能按“请记住”处理？

前者是在读取已有记忆，后者是在执行新的写入副作用。使用“文本中包含记住”这种宽泛
规则会混淆读写语义，导致读取请求被送入写入服务。uPil 只把句首祈使表达识别为写入
命令，并把“以前记住、已经记住、还记得吗、不要记住”作为读取或否定边界；最终仍由
结构化准入和权限服务决定能否落库。

## Q41：为什么已经把长期偏好拼进 RAG Query，还要增加确定性读取回答？

RAGFlow 的资料可能包含旧客服能力说明，模型也可能根据通用客服习惯回答“无法读取
个人信息”。但偏好是否存在是 PostgreSQL 中的应用事实，不应交给知识库生成判断。
用户明确引用已保存偏好时，uPil 直接读取安全投影并生成受控回答；RAG 继续负责课程
知识。这样既避免否定真实能力，也不允许偏好伪造实时班次、价格或名额。

## Q42：为什么代码已经实现，页面仍可能表现为功能未实现？

代码只是能力的一部分。页面实际使用哪个镜像、哪份环境文件、数据库是否完成迁移、功能开关是否开启、外部依赖是否真的可用都会改变运行结果。uPil 曾因 staging 私有环境遗漏 `MEMORY_WRITE_ENABLED=true`，导致已有长期记忆代码返回 disabled。现在通过启动校验、静态配置审计、镜像重建和真实 HTTP 冒烟共同验收，而不是只看单元测试。

## Q43：如何防止环境模板漂移？

把关键配置关系编码为可测试契约，并让审计脚本同时扫描开发示例、staging 示例、生产示例和 Compose。废弃变量一旦出现即失败；受管环境必须显式满足 Redis、记忆、PDF/MinIO 和 RAGFlow 成组约束。私有密钥文件不提交，但同名 example 必须包含完整键集合。

## Q44：为什么根 `.env` 不直接配置 `extra="forbid"`？

根 `.env` 是多个同仓组件共享的部署输入，其中 Docker、RAGFlow 或脚本变量对 API Settings 来说是合法的“未知字段”。直接 forbid 会把组件边界混成一个模型。uPil 让 Settings 校验应用字段，再由独立审计器识别明确废弃键和跨组件契约，严格但不过度耦合。

## Q45：为什么使用两个 RAGFlow Assistant？

公开课程咨询和请假、调课等服务规则的知识来源、提示约束和更新频率不同。拆分后可分别召回、评测和降级，避免课程资料污染办理规则，也避免单个 Chat ID 成为不可解释的大杂烩。Supervisor 先决定知识域，Connector 只调用对应 Assistant。

## Q46：数据库健康为什么不等于长期记忆可用？

数据库 Ping 只能证明连接存在；长期记忆还依赖迁移表、写入开关、认证作用域、准入策略和事务提交。uPil 的 `structured_memory` 探针检查运行开关和存储结构，真实冒烟再验证写入、跨 conversation_id 读取和精确清理。

## Q47：RAGFlow 首页能打开为什么仍可能无法问答？

Web 首页只验证 Nginx/RAGFlow 应用可达。一次 RAG 查询还要经过 Assistant 配置、查询 Embedding、Elasticsearch 检索和回答模型。Ollama 未运行或容器无法访问宿主机时，首页仍可能是 200，但查询会报 102 Embedding failure。

## Q48：如何检测 Embedding 停机？

部署检查分三层：访问 Ollama `/api/tags` 确认服务与 `bge-m3:latest`；从 RAGFlow 容器访问 `host.docker.internal:11528` 验证容器网络；调用 uPil 深探针完成一次真实双知识域问答。三层能区分模型缺失、本机端口、容器网络和业务链路故障。

## Q49：为什么区分浅探针和深探针？

浅探针快速、便宜、可高频，适合编排器判断进程是否可服务；深探针会真实检索和推理，可能触发冷启动并产生模型成本，只适合发布验收和故障诊断。若把深探针用于秒级健康检查，反而会制造负载和误报。

## Q50：健康检查如何避免泄露 Token 和内部信息？

深探针只返回固定依赖名称和低基数状态枚举，不回显请求、答案、来源、Assistant ID、模型、URL、异常正文或凭据。详细错误只进入受控服务端日志，且日志同样不记录密钥。

## Q51：为什么 PDF 开启时必须要求 MinIO？

正式报告是跨实例可下载且要审计的私有产物。本地临时文件无法保证下一次请求仍落在同一实例，也难以统一生命周期和权限。uPil 因此把 PDF 与 MinIO 设为强依赖：上传或完整性校验失败时任务失败，不展示半成品。

## Q52：如何确认运行的是新镜像而不是旧容器？

修改代码后显式执行 Compose build 与 force-recreate，等待容器 healthy，再调用新增接口或检查镜像摘要。只重启旧容器不会包含新代码。最终以运行中 HTTP 行为和依赖探针为准，而不是以本地文件内容为准。

## Q53：为什么真实冒烟后必须精确回收数据？

真实链路会产生会话、长期偏好、报告任务、MinIO 对象和下载审计。若不清理会污染用户页面与后续幂等测试；若全表清空又会破坏他人数据。uPil 记录本轮 conversation/task/object ID，按资源依赖顺序精确删除并复核计数为零。

## Q54：为什么长期偏好已经写入 PostgreSQL，Agent 仍可能回答“不记得”？

写入成功不代表每种自然问法都能触发读取。uPil 曾只支持“根据以前记住的偏好推荐课程”，而“你还记得孩子的小名吗”被 Supervisor 判为 UNKNOWN，随后直接进入澄清节点。修复不是重复写入或把全部历史塞进 Prompt，而是在身份隔离读取之后增加白名单字段级回忆，并在路由执行前覆盖明确命中的 UNKNOWN。

## Q55：字段级长期记忆为什么不用向量检索或 RAG？

昵称、课程兴趣和上课时间是已知 key 的结构化事实，关系库精确读取更可靠、可解释，也更容易做用户隔离和更正。向量检索适合不知道 key 的模糊历史片段，不适合回答“孩子的小名是什么”这类精确事实。uPil 因此用固定问法映射到白名单 key，字段不存在时明确说未保存，并且只返回用户询问的字段。
