# 项目收尾答辩：为什么移除 A2A 并统一学情分析 Agent

## Q1：为什么之前做过 A2A，现在又移除了？

**答：** 阶段 13 的目标是验证跨进程任务契约、脱敏、状态、重试和故障隔离，这些实验已经完成。但当前项目的学情能力在同一代码库、同一权限域和同一团队内运行，报告又是本地固定模板生成，没有独立扩缩容、异构运行时或跨团队部署需求。继续保留远程协议只会增加网络、令牌、健康检查和状态映射成本，所以现行版本选择同进程统一学情分析 Agent。

## Q2：移除 A2A 是否等于放弃多 Agent？

**答：** 不是。A2A 解决的是跨进程 Agent 协作协议，LangGraph 解决的是进程内多 Agent 编排。当前仍保留 Supervisor、FAQ、服务规则、统一学情分析、报课意向和人工转接等职责边界。学情分析 Agent 内部再分为个人摘要、家长报告和班级报告处理器，拥有不同的输入契约、工具边界和失败策略。多 Agent 不要求每个 Agent 都必须是一个独立服务。

## Q3：为什么个人学情、家长报告和教师班级报告不各自部署成三个 Agent？

**答：** 三者都依赖主系统的授权结构化数据，差异主要是展示对象、统计维度和报告字段，而不是独立运行时。统一入口可以复用权限、周期解析、任务状态、PDF、MinIO 和下载鉴权；内部处理器保持单一职责，仍然可以独立测试和替换。只有出现独立团队、独立资源池或明显不同的伸缩曲线时，才值得拆成远程服务。

## Q4：统一 Agent 会不会重新变成一个大总控文件？

**答：** 不会。Supervisor、State Schema、路由、Builder、节点、Tool、Service 和 Prompt 分开维护；一个节点一个文件。`learning_analysis_agent` 只做能力选择和边界衔接，个人摘要、家长报告和班级报告的具体逻辑分别下沉到处理器和报告服务。当前生产 Python 文件最大 485 行，超过 800 行为 0；800 行只是门禁，真正的判断依据仍是单一职责和依赖方向。

## Q5：统计数据如何避免被模型或模板改错？

**答：** 课时、出勤、完课率、缺勤排行、低课时和缺失考勤由数据库查询和确定性统计计算。模型不负责计算这些数字；当前报告正文使用固定模板。渲染前后都对照权威快照校验字段，PDF 再由 `pypdf` 复核标题、页数、摘要和敏感标识，任一校验失败就进入失败状态，不展示半成品。

## Q6：报告链路现在如何保证私有下载？

**答：** 新任务只保存一个 PDF Artifact。PDF 上传到私有 MinIO 桶，浏览器不获得预签名 URL、对象键、桶名或存储地址；下载请求先由 FastAPI 重新校验家长当前绑定孩子或教师当前授课班级，再读取并校验对象后代理返回。关系被撤销后，历史任务也立即不可访问。

## Q7：为什么 Markdown 不再作为报告产物保存？

**答：** 当前验收目标是可阅读、可打印的 PDF。Markdown 只是模板到 PDF 的内存中间态，保存 Markdown 会引入第二个产物、第二套下载权限和格式一致性问题。保留中间态便于转换和测试，但对外和持久化边界只有 PDF。

## Q8：报课意向 Agent 是否也需要 A2A？

**答：** 当前不需要。它是同一轮消息的异步旁路识别，输出有限的意向证据和联系方式授权状态，不回答用户、不持有数据库会话，也不需要独立部署。入口先在本地脱敏联系方式，只有家长主动提供并明确同意联系、且达到有效意向条件时才加密保存。若未来招生识别由独立团队维护或需要独立容量，再评估远程协议。

## Q9：不用 A2A 后，项目的技术价值在哪里？

**答：** 技术价值来自业务边界和可验证性：Supervisor 的多意图编排、多轮指代消解、FAQ 来源约束、结构化 Tool、权限与数据最小化、确定性统计、固定 PDF、私有对象存储、动态下载鉴权、旁路意向识别和人工兜底。选择更简单的同进程架构，是根据实际运行边界做出的工程判断，不是减少技术含量。

## Q10：当前能否宣称生产就绪？

**答：** 不能直接宣称。当前完成的是本地可验证的业务闭环和自动化测试；真实 OIDC、PostgreSQL、MinIO、RAGFlow、模型、机构数据、容量、容灾和安全联调仍需在目标环境完成。阶段 13 的 A2A/DSH 联调结果只说明历史实验完成，不代表当前运行时仍包含这些服务。
