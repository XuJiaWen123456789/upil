# uPil 多 Agent 意图仲裁与会话状态机面试问答

> 日期：2026-09-15
> 适用主题：Supervisor、LangGraph、多轮对话、主/旁路意图、槽位门禁、上下文共享、测试治理

## Q1：这个项目的意图识别最终是怎么实现的？

不是只调用一次大模型做分类，而是分成四层：第一层做身份、权限、联系方式脱敏和
高精度确定性守卫；第二层解析实体、指代、纠错和槽位；第三层在确定性规则无法覆盖时
可选调用 Supervisor 模型；第四层由对话仲裁器把模型结果、会话状态和 pending 统一成
不可变 `TurnDecision`，最后 LangGraph 只负责执行确定后的业务路由。

这样既保留模型对自然语言的泛化能力，又不让模型直接决定权限、数据库范围和副作用。

## Q2：为什么不能让 TurnDecision 一次 LLM 调用完成全部事情？

意图、实体、槽位、pending 和副作用级别的约束不同。把它们全部交给一个 Prompt，
会增加 JSON 缺字段、冲突字段和高风险参数被猜测的概率。uPil 可以在内部保留一次模型
分类以控制成本，但身份、取消、联系方式、确认槽位和 pending 恢复由确定性代码处理，
最后再仲裁，而不是要求模型一次性拥有所有决策权。

## Q3：TurnDecision 解决了什么问题？

它把“这一轮系统究竟认为用户在做什么”固化成唯一契约，包括主意图、旁路意图、
对话行为、活动实体、槽位来源、pending、缺失参数、最终路由和副作用等级。主业务
Agent 和招生旁路读取同一对象，不再分别猜测。因此它既是执行契约，也是测试和
可观测性的最小数据模型。

## Q4：为什么 TurnDecision 要不可变？

如果多个 Agent 共享一个可写字典，FAQ Agent 修改活动课程后，招生 Agent 可能在同一轮
看到另一个课程，最终产生难以复现的竞态。冻结 dataclass 加只读映射能保证所有 Agent
看到同一版本；需要更新时必须在下一轮经过状态机重新生成，而不是就地篡改。

## Q5：确定性规则和模型如何分工？

确定性规则负责高精度、高风险和可枚举场景，例如问候、取消、联系方式、年龄、明确
课程名、自然语言周期、实时名额、报告查看与生成分流。模型只处理规则未覆盖的开放表达。
发生冲突时，身份权限、用户明确原话和确定性守卫优先，模型不能覆盖这些事实。

## Q6：为什么“你好”不应该进入 RAG？

问候不需要知识检索。进入 RAG 会增加延迟和成本，还可能让知识库根据机构文档生成
一段冗长介绍，造成“只会回复宣传话术”的体验。本项目通过固定 `small_talk` 节点回答，
专项测试还显式禁止调用 FAQ，证明调用次数从 1 次降为 0 次。

## Q7：UNKNOWN 为什么要细分？

UNKNOWN 不是一种业务行为。“你好”是寒暄，“这个课程多少钱”可能是缺少指代上文，
“股票走势”是域外问题，“现在有名额吗”是机构域内但需要实时系统。若全部送 FAQ，
知识库会对不该回答的问题生成看似合理的内容。uPil 因此拆成 small_talk、
needs_clarification、unsupported_in_domain、out_of_scope、in_domain_general 和 unknown。

## Q8：信息不足和完全域外有什么区别？

信息不足仍有可完成的业务目标，例如“这个班多少钱”缺少课程名，应追问具体课程；
完全域外则不应该追问课程，而应说明当前只处理教培咨询。两者都不进入 FAQ，但回复策略
不同，这也是 UNKNOWN 细分类的价值。

## Q9：主意图和旁路意图如何定义？

主意图决定用户当前等待的主要回答；旁路意图是不应抢占主回答、但可触发附加分析的
次要诉求。例如“这个班多少钱，我还想预约试听”，价格是主意图，试听是旁路意图。
FAQ 回答价格，报课意向 Agent 并行识别试听并更新线索，两者互不覆盖。

## Q10：为什么报课意向 Agent 是旁路而不是主路由？

家长首先需要得到当前问题的答案。如果检测到意向就立刻切换成销售话术，会破坏咨询
体验，也会让多 Agent 看起来只是技术堆叠。旁路模式让主 Agent 正常答疑，招生 Agent
只产出线索建议；只有高意向且缺少已授权联系方式时，系统追加固定授权询问。

## Q11：pending flow 是什么？

pending flow 是尚未收集完整参数的受控业务状态，不是把整段历史对话继续塞进 Prompt。
例如报告生成缺少周期时，状态中保存 `learning_report` 和缺失的 period_start/period_end。
下一轮用户只说“上个月”，状态机就能恢复报告任务。

## Q12：pending 为什么不能一直优先？

如果 pending 无条件最高优先级，用户转而问请假或明确取消时，旧报告任务会劫持新问题。
因此顺序是：显式取消优先；兼容的槽位补全可以恢复；礼貌插话保留；明确新业务则切换。
这在任务连续性和用户控制权之间取得平衡。

## Q13：如何处理“报告→谢谢→上个月”？

第一轮建立报告 pending；第二轮被识别为 courtesy，只走 small_talk 并保留 pending；
第三轮自然语言周期解析器得到确认日期，状态机恢复 learning_report 并清除已完成的 pending。
整个过程不访问 FAQ，也不要求用户填写开始和结束日期。

## Q14：槽位为什么要记录来源？

相同的值来自不同来源时可信度和使用权限不同。用户明确说“上个月”和模型从摘要中猜
“可能是上个月”不能等价。`SlotValue` 保存 source、confidence、confirmed，使业务层能
执行统一门禁，而不是每个节点自行判断。

## Q15：模型推断槽位能不能直接调用报告工具？

不能。报告周期、班级和学员范围会影响数据库查询与产物生成，属于有副作用或授权敏感
参数。模型推断值默认 `confirmed=False`，只能用于澄清候选；用户明确提供、白名单解析、
已确认会话值或授权数据库范围才允许进入工具。

## Q16：模型推断槽位全部禁止，会不会过于保守？

门禁按风险分级，不是全面禁止模型。课程兴趣、一般咨询可以使用模型语义；报告范围、
班级统计、联系方式授权必须确认。对个人求职项目而言，这比追求“任何一句话都自动执行”
更能体现生产思维。

## Q17：项目如何做指代消解和用户纠错？

Redis 会话保存已确认活动实体、近期窗口和滚动摘要。用户说“那个班”时只在存在已确认
课程上文时重写查询；没有上文则进入专用澄清。用户说“我说错了，是素描基础班”时，
纠错实体覆盖旧实体，后续“那个班”指向新课程。

## Q18：上下文压缩会不会丢失关键槽位？

关键槽位不只存在自然语言摘要中。项目保留最近原始轮次、滚动摘要、已确认活动实体、
pending 和结构化槽位。摘要负责压缩历史语境，结构化状态负责保证主意图和关键参数不被
压缩丢失，因此不是把全部历史压成一段自由文本。

## Q19：多 Agent 共享上下文具体怎么做？

请求边界装配一个最小 `ContextEnvelope`，其中包含不可变 TurnDecision、授权上下文、
已确认实体、短期窗口、摘要和安全长期偏好投影。不同 Agent 使用 projector 读取自己的
最小视图，不能共享联系方式明文、数据库 Session 内部状态或可写大字典。

## Q20：为什么不使用 A2A 做上下文共享？

当前 Agent 都在同一 FastAPI/LangGraph 进程和同一业务事务边界内。A2A 会增加网络协议、
鉴权、序列化、超时、幂等和部署成本，却不能提升这里的意图一致性。不可变进程内契约
更直接。只有 Agent 属于独立团队、独立服务、独立伸缩和独立故障域时才值得重新评估 A2A。

## Q21：为什么不把全部对话写入向量数据库？

本次问题主要是短期状态、指代和结构化槽位，不是历史情景召回。完整对话无筛选入库会
造成记忆污染、隐私风险和无关召回。当前 Redis 管短期会话，PostgreSQL 管低敏感稳定偏好，
程序性规则由代码和 Prompt 管理；情景向量记忆保持可替换但默认关闭。

## Q22：多用户会话如何隔离？

会话键不只使用 conversation_id，还绑定租户、用户、角色和可选学员作用域。测试覆盖了
两个家长使用相同 conversation_id：第二个家长不能读取第一个家长的课程实体。长期偏好
读取同样按授权主体和学员范围过滤。

## Q23：为什么 SSE 需要暴露主意图和 UNKNOWN 类型？

只有最终 route 无法判断错误发生在分类、仲裁还是图执行。SSE complete 增加白名单枚举后，
可以离线统计主意图混淆、旁路漏检和 UNKNOWN 分布。字段不包含用户原文、槽位值和身份
标识，因此兼顾可观测性与隐私。

## Q24：如何评估这套意图系统？

至少分四组指标：主意图准确率与混淆矩阵；旁路意图 precision/recall；槽位值、来源和
确认状态错误；pending 建立、保留、恢复、取消成功率。另统计 UNKNOWN 分布、澄清后完成率、
RAG 无效调用率和高风险工具误触发率，不能只看一个分类准确率。

## Q25：这次优化有什么可量化效果？

自动化测试证明：纯问候、域外问题和无上文指代的 FAQ/RAG 调用从 1 次降为 0 次；
礼貌插话后报告任务可恢复；价格和试听复合诉求不再丢失价格主回答；未确认模型周期不能
调用报告；同一日期范围的不同自然语言表达复用同一 PDF。后端全量为
`553 passed, 8 skipped`，前端为 `20 passed`。这些是确定性回归效果，不冒充线上准确率。

## Q26：全量测试发现了什么专项测试没发现的问题？

先前一个 API 测试用显式日期生成 2026 年 8 月报告，新增测试用“上个月”生成同一范围。
两者任务哈希相同，但 scope 中的 period_type 不同，旧幂等判断把它当成冲突。专项单独运行
时数据库是干净的，因此没有暴露；全量顺序组合发现了问题。最终将 period_type 从业务
同一性比较中排除，并增加专门回归。

## Q27：为什么 period_type 不应参与报告幂等键？

它只是用户表达形式。`2026-08-01 至 2026-08-31` 和当时语境中的“上个月”指向同一数据
范围。真正决定报告内容的是请求人、报告类型、业务对象、起止日期和模板版本。把展示元数据
放进幂等键会重复生成或冲突，违背“相同学员、相同周期避免重复生成”的业务要求。

## Q28：为什么还保留 LangGraph，而不直接写 if/else？

if/else 适合确定性守卫和仲裁；LangGraph 适合把 FAQ、服务规则、学情、报告、人工处理等
执行节点显式编排、测试和扩展。项目没有用图替代所有代码，而是让状态机负责决定，图负责
执行，这比把权限和槽位解析都塞进图节点更清晰。

## Q29：如何避免单文件继续膨胀？

对话决策拆成 contracts、slots、unknown、classification、pending、arbitration；LangGraph
每个边界节点单独文件；业务执行仍在 service 层。当前生产 Python 最大 599 行，超过
800 行为 0。文件数量增加是为了单一职责，不是把一个函数机械切碎。

## Q30：这套方案还有哪些生产增强空间？

第一，基于真实脱敏测评集调阈值并记录模型校验/重试指标；第二，将 FastAPI 启动事件迁移
到 lifespan；第三，有明确容量目标后再做 Redis 高可用和报告异步 worker；第四，只有情景
召回通过离线评测后才启用 Embedding。当前个人求职项目已经完成可解释、可测试的闭环，
不需要为了技术名词继续增加分布式组件。

## Q31：为什么 Supervisor Router 要固定 temperature=0？

Router 负责输出结构化意图和字段，不负责创作自然语言。相同输入如果因采样产生不同
分类，会让路由、成本和副作用都难以复现。因此 uPil 在依赖工厂中显式传
`temperature=0`，不继承普通回答模型的温度。零温度不能保证模型永不出错，所以后面
仍有 Schema 校验、业务白名单、确定性回退和状态机仲裁。

## Q32：是否必须给 Router 使用单独的模型？

不必须。项目支持 `LLM_ROUTER_MODEL`，便于以后选择更便宜或分类更稳定的模型；未配置
时复用 `LLM_MODEL`。当前本地复用 `deepseek-chat` 更符合个人项目的成本和部署边界。
真正重要的是固定零温度、输出校验、回退和评测，而不是为了简历强行增加一个供应商。

## Q33：为什么增加 few-shot 后还需要确定性状态机？

few-shot 只能帮助模型区分高混淆语义，例如“查看报告”和“生成报告”，不能可信地
处理身份权限、联系方式授权、报告周期确认和 pending。样例还可能随着课程目录变化而
漂移，因此运行时白名单从代码动态注入，模型输出继续经过业务校验；高风险副作用由
确定性规则决定。

## Q34：主意图混淆矩阵如何建立？

每条脱敏评测样本保存 expected intent 和实际 intent，矩阵的行是期望、列是实际。基于
矩阵计算每类 TP、FP、FN、Precision、Recall 和 F1，同时保留总体 accuracy。这样可以
看出 `report_history` 是否经常被误判成 `learning_report`，而不是只看到一个总体分数。
真实模型评测必须显式运行，普通 pytest 不访问模型供应商。

## Q35：为什么不能只评测单轮分类？

很多缺陷发生在第二、第三轮，例如“报告→谢谢→上个月”、课程纠错后的“那个班”、
相同会话编号下的用户隔离。uPil 增加离线多轮评测，分别统计路由、主/旁路意图、
UNKNOWN、槽位值/来源/确认状态，以及 pending 建立、保留、恢复、取消成功率。当前
12 组、20 轮确定性回归集全部为 100%，但不会把该结果包装成线上模型准确率。

## Q36：为什么日志不记录 Prompt、消息正文和模型原始输出？

这些内容可能包含儿童信息、联系方式、身份编号、内部规则和供应商异常细节，复制到日志
会扩大泄露面。问题定位真正需要的是 route、意图枚举、UNKNOWN、缺失槽位名、槽位来源、
回退原因和耗时。项目使用白名单 `DecisionEvent`，连 route 和失败原因都不接受自由文本。
思维链既不是稳定业务契约，也不应该作为可观测字段。

## Q37：模型未配置或失败时如何诊断？

识别服务只返回三个安全原因：`model_not_configured`、
`invalid_or_timed_out_model_output`、`model_provider_error`。日志不保存供应商异常正文；
结合 `decision_source`、最终 route 和耗时，就能区分“本来走确定性规则”“未配置模型”
和“模型调用后降级”，同时避免把密钥或请求内容带入日志。

## Q38：第三阶段优化的实际收益是什么？

第一，零温度和专用模型配置让 Router 可重复、可独立调优；第二，few-shot 补足高混淆
表达；第三，混淆矩阵与多轮指标把回归变成可量化结果；第四，结构化决策日志可以定位
线上回退和延迟，同时保持隐私边界。本阶段还通过评测发现并修复“生成上个月的学情
报告”未命中确定性生成守卫的问题，证明评测并非只为展示指标。

## Q39：为什么“它需要自己买乐器吗”不应该每次都走 RAG？

因为课程是否提供课堂乐器属于低频变化、可枚举的稳定课程属性。先完成“它”到童声合唱班
的指代消解，再从受控课程目录确定性回答，延迟更低、结果可审计，也不会因 RAGFlow 的
Embedding 或网络故障返回 503。RAG 仍用于开放式课程说明，不是所有事实的唯一入口。

## Q40：既然 RAGFlow 客户端已经捕获网络异常，为什么服务层还要兜底？

客户端只能覆盖它已知的异常类型；第三方 SDK、自定义适配器和测试桩可能抛出其他异常。
服务门面是聊天主链路与外部系统的最后边界，必须把未知外部异常收敛成安全离线结果，
保证 SSE 正常结束，同时不把 URL、Token、堆栈或供应商错误正文暴露给用户。

## Q41：如何处理“现在有名额吗？费用多少？”这种复合诉求？

主路由可以只有一个，但请求属性不能只保留一个。uPil 在决策中同时保存
`available_seats` 和 `price`，人工兜底节点根据属性集合同时说明名额和费用边界。这样
既避免编造实时数据，也避免“路由到名额后吞掉价格”的信息损失。

## Q42：为什么“不用联系我”会被错误识别成要联系？如何修复？

简单子串规则会在“不用联系我”中命中“联系我”；同时联系方式 pending 若先于取消判断，
还会抢占普通仲裁。修复采用双层门禁：否定短语先于正向关键词；联系方式补全执行前再次
检查明确拒绝。拒绝轮随后撤回线索并清除联系方式数据，保证回答和后台状态一致。

## Q43：本轮修复如何证明不是针对单个测试样本打补丁？

课程装备按属性和 9 个正式课程建模；多轮回归覆盖舞蹈、美术、音乐和编程，包括纠错、
插话、指代恢复、实时名额、费用、试听和联系方式拒绝。专项为 `121 passed`，相关回归
`154 passed`，后端全量为 `613 passed, 8 skipped`。覆盖的是通用决策边界，而不是只匹配
“童声合唱班”一句话。
