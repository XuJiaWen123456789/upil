# 家长实时学情与报告入口分流：面试问答

## Q1：为什么“查看阶段反馈”不能继续走 RAG？

因为 RAG 适合回答稳定知识，不适合返回用户专属动态数据。阶段反馈、课时和出勤受身份与学员绑定关系约束，必须读取授权数据库；否则只能得到“通常会反馈哪些内容”的泛化答案，既不满足业务，也可能产生越权风险。

## Q2：为什么不用 LLM 统一判断查看和生成报告？

两者副作用不同。查看历史只导航，生成报告会创建任务、生成 PDF 并写 MinIO。对有副作用的边界，项目采用确定性关键词守卫和白名单枚举，让模型只能参与低风险语义补充，不能自由触发任务。

## Q3：为什么家长不需要输入 learner_id？

`learner_id` 是内部资源标识，不应成为真实家长的交互知识。服务端根据认证用户查询绑定关系：只有一个有效孩子就自动解析；有多个孩子则让家长按姓名选择。这样同时兼顾易用性和权限正确性。

## Q4：多个孩子为什么不能默认选择第一条？

数据库排序不是用户意图。默认第一条可能把另一个孩子的学情展示出来，属于严重的对象错配。项目只在唯一绑定或消息唯一命中孩子姓名时自动解析，其余情况必须澄清。

## Q5：为什么越权和不存在返回相同提示？

如果“存在但无权”和“不存在”的错误不同，攻击者可以批量尝试编号并判断哪些学员真实存在。统一提示可以减少资源枚举信息，同时仍能指导合法用户检查账号绑定。

## Q6：如何防止教师内部备注泄露给家长？

不是依赖 Prompt 要求模型“不要说”，而是在数据契约和叙事生成层只使用已发布字段。`teacher_note` 不参与家长摘要拼装，测试还使用已知备注内容做负向断言。

## Q7：历史报告按钮为什么要前后端双白名单？

后端只签发固定 `/parent/reports`，前端也只接受同一路径。后端控制业务契约，前端防止异常响应、未来误改或不可信内容变成开放重定向和脚本执行入口，属于纵深防御。

## Q8：如何证明“查看学习报告”没有偷偷生成报告？

API 测试在请求前后统计 `ReportTask` 数量，并断言 SSE 中没有 `report_task` 状态事件；同时禁止 FAQ 被调用，最终只允许 `report_history` 路由和固定站内导航动作。

## Q9：这一设计体现了 Agent 项目的什么工程价值？

它不是让所有请求都经过 LLM，而是让 Supervisor 按风险选择执行器：稳定知识走 RAG，动态个人数据走授权工具，历史资源走受控导航，有副作用的生成任务走显式工作流。Agent 的价值体现在正确编排能力边界，而不是模型调用次数。

## Q10：测试结果如何？

意图、会话、图、学员解析和 API 核心专项 135 条通过；相关多轮、记忆、学情、
报告和招生线索回归 162 条通过；前端聊天专项 5 条通过；后端全量 534 条通过、
8 条按环境跳过。typecheck、compileall 和 diff check 均通过。

## Q11：用户只说“生成学情报告”，为什么不直接默认最近一个月？

报告生成会创建任务、生成 PDF 并写入私有对象存储，属于有副作用操作。默认周期
可能生成用户不需要的报告，也会影响相同学员、相同周期的幂等判断。项目使用
`pending_intent` 暂存已确认的报告意图，提示家长用“本月、上个月、最近30天”等
自然语言补充；下一轮由确定性日期解析器恢复流程，而不是要求填写后台表单。

## Q12：为什么澄清问题不交给 LLM 自由生成？

澄清节点处在数据库查询和任务创建之前。自由生成虽然语言灵活，但可能遗漏必要参数、
暗示系统已经完成生成，或引入未经支持的周期。项目按照白名单意图选择固定业务模板，
既能承接当前上下文，也让缺失参数和允许的回答形式可测试、可审计。
