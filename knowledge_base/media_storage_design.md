# 图片与复杂文档存储设计

## 总体方案

文档和图片进入三项职责清晰的协作链路：RAGFlow 负责正文、表格、OCR 文本、图片说明和检索来源；MinIO 负责教师照片、校区环境图、课程表原图、PDF 和课件等二进制对象；PostgreSQL 记录媒体资产的标题、替代文本、来源文档、可见范围、审核状态、内容哈希和 MinIO 对象键。

## 为什么图片不直接放进 PostgreSQL

本项目的 PostgreSQL 主要保存用户、学员、课程、课次、出勤和任务等结构化业务事实，同时保存媒体元数据。图片属于非结构化媒体资产，使用 MinIO 可以按对象方式保存，并通过 S3 兼容接口支持大文件、分桶、权限、备份和预签名 URL，避免把二进制写入业务数据库。

MinIO 兼容 S3 协议，未来可以在不修改业务接口的情况下迁移到云对象存储。uPil 通过对象存储适配器隔离具体 SDK，业务代码不直接拼接 MinIO URL。

## RAGFlow 如何使用图片

图片本身不等于可检索知识。上传前需要同时准备图片原文件、图片标题和替代文本、图片所属文档和业务主题、必要时的 OCR 文本或人工描述，以及 media_asset_id 与审核状态。

RAGFlow 负责对文档、表格和 OCR 内容做解析和检索；uPil 负责媒体权限和资产读取。涉及学员个人照片时，必须使用私有可见范围并经过登录态校验，不能把图片直接作为公开 FAQ 资源。

## 安全规则

- 教师照片必须取得授权并记录审核状态。
- 学员照片、身份证件、家长联系方式不能进入公开知识库。
- SVG 等可执行性较强的格式上线前应进行消毒或转换为 PNG/WebP；当前 SVG 仅用于本地演示插图。
- 不在回答中返回 MinIO 密钥、内部桶名或对象存储管理地址。
- 媒体下载接口必须接入登录态和访问范围校验，不能仅凭文件 ID 公开读取；通过校验后只生成短时预签名 URL。
- RAGFlow 和 uPil 使用不同的 MinIO 凭证与桶权限，避免一个服务读取不属于自己的对象。
